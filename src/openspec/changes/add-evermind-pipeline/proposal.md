## Problem

A support knowledge base only answers what someone thought to write down.
Every question it misses is answered by a human instead — and then
forgotten, because nothing captures the miss. The same question gets asked
again the following week and costs the same twenty minutes.

**Who feels it.** The knowledge-base content owner, asked to keep the base
current with no reliable signal about what is missing, so entries get
written from anecdote rather than demand. The customer feels it too: they
get nothing, and escalate.

**Why an agent.** The work is repetitive and ends in a decision, not a
summary: read the unanswered questions, group the ones that mean the same
thing, check whether an answer already exists, find the source that supports
a new one, draft it. One model call cannot do it — deciding "do we already
answer this?" requires looking in the knowledge base, and drafting a
grounded answer requires retrieving the evidence first.

## Solution

A batch agent that turns a log of unanswered questions into reviewed,
source-cited FAQ candidates.

**Inputs.** A batch of logged questions, the knowledge base, and a corpus of
trusted source documents.

**Decisions the agent makes.** Which questions mean the same thing; whether
a group is a genuine gap, a rephrasing of an existing entry, or a question
the base should not answer; which retrieved passages actually support an
answer; and whether the evidence is strong enough to draft at all.

**Output shape.** One `FAQCandidate` per group — a validated Pydantic model,
not free text:

| Field | Constraint |
| --- | --- |
| `gap_id`, `representative_question`, `cluster_size` | identity and coverage |
| `disposition` | `HUMAN_REVIEW` \| `DUPLICATE_OF_EXISTING` \| `REJECT_OUT_OF_SCOPE` |
| `proposed_answer` | ≤ 150 words; `None` unless `HUMAN_REVIEW` |
| `source_citations` | ≥ 1 whenever an answer is present |
| `confidence`, `reason` | 0.0–1.0; a reason on every refusal and duplicate |

A validator enforces the cite-or-reject rule: **an answer with no citation
is not a weak answer, it is an invalid object** and never reaches a
reviewer.

**Nothing is published without a human.** The agent writes one queue file.
Publishing is a separate human step.

## Scope

**In.** Grouping, the three-way disposition, retrieval over the trusted
corpus, drafting with citations, the review queue, and the seeded
demonstration data.

**Out.** Publishing to the knowledge base (no write path exists), live web
search, auto-approval at any confidence, multilingual handling, a review UI,
and answering customers directly. EverMind builds content; it is not a
chatbot.

## The demonstration data is ours

Greenfield in full: no external system, no integration to negotiate. The
knowledge base, the query log and the source corpus are generated by
`tools/build_fixtures.py` from one seed and committed, so a clean checkout
runs with no credentials and no network.

| Fixture | Contents |
| --- | --- |
| `faq_store.json` | 45 published entries across six topics — what we grow |
| `query_log.json` | 59 unanswered questions, each labelled with its expected disposition |
| `sources.json` | 15 documents, 31 passages — the only evidence a draft may cite |

The labels are the point. **The answer key lives in a file the agent never
reads**, which is what turns the eval set from "does this look reasonable?"
into "did it get the right answer?" Breakdown: 29 genuine gaps (three
deliberately unsupported by any source), 15 duplicates, 10 out of scope
including one prompt injection, 5 deliberately ambiguous.

## Risks and guards

| # | Risk | Guard | Evidence |
| --- | --- | --- | --- |
| R1 | The agent drafts an answer the sources do not support. A confident wrong entry is worse than none: it gets approved, then served to everyone. | A citation must name a passage retrieved in that run. The validator rejects an uncited draft before a reviewer sees it. | Main path + failure path |
| R2 | Fifteen rephrasings become fifteen near-identical drafts and the reviewer stops reading. | Grouping runs before any model call; a group matching a published entry returns as a duplicate, not a draft. | Edge case |
| R3 | Answers drafted for questions the base should not answer — account specifics, complaints, commercial terms. | Refusal is a first-class outcome with a required reason, decided before retrieval. The prohibited work is never done, not discarded after. | Policy case |
| R4 | A logged question contains instructions aimed at the agent. One fixture is exactly this. | Logged text is data, never instruction. No tool writes anywhere, so the worst case is a bad draft a human rejects. | Adversarial case |
| R5 | A candidate reaches the knowledge base without approval. | Structurally impossible — the only output is a queue file. | Write-path regression |

## Build sketch

**Start with one `LlmAgent` carrying both the tool calls and the
`output_schema`.** ADK 2.x supports this on a single agent, and both
capstone samples are single agents. Escalate only if the problem demands it.

| Construct | Why |
| --- | --- |
| `LlmAgent` + Pydantic `output_schema` | One validated answer per group |
| `FunctionTool` ×3 — existing-entry search, scope check, source retrieval | Read-only lookups; keeps bulk text out of the prompt |
| Session state | Retrieved passage ids, read back by the validator to verify citations |
| `after_tool_callback` | The audit line a reviewer traces a claim through |
| `AgentEvaluator` + pytest | The regression gate |

**Not planned:** memory service (nothing persists across runs), A2A or
sub-agents (no separate steps yet established), MCP server (nothing to
expose), response caching (unsafe for this).

**Honest sizing.** One agent, three tools, three people, Tuesday to
Thursday. If the model turns out not to support tools and `output_schema`
together — a limit the WA3915 guide flags as model-dependent — the fallback
is to split retrieval from formatting across two agents. That is a known
exit, not a promise to build a multi-agent system.

## How we will prove it works

An eval set built from the answer key, plus deterministic tests that run
without an API key.

| Case | Asserts |
| --- | --- |
| Main path | A supported gap → `HUMAN_REVIEW`, cited, within the word limit |
| **Failure path** | An unsupported gap → **no answer**, low confidence. The agent declines rather than invents. |
| Edge case | A rephrasing → `DUPLICATE_OF_EXISTING`, naming the entry, no draft |
| Policy | An account-specific question → refused, **and retrieval never called** |
| Adversarial | The injection → treated as data, refused, no anomalous tool call |
| Regression | A full run leaves the knowledge base byte-for-byte unchanged |

## Architectural considerations

| Concern | Position |
| --- | --- |
| **Security** | Tool access is least-privilege by construction: three read-only functions, no write function implemented or imported, so no model decision can publish. No network and no credentials in the test path — fixtures are local. Logged text is untrusted input; one fixture is an injection, as an eval case rather than a footnote. |
| **Reliability** | Validation is the degradation boundary: a malformed or uncited candidate fails closed and is queued as a refusal rather than crashing the batch. A tool failure returns a typed error the agent must handle. Batch, not interactive — a failed run is retried over the same log with no user-visible effect, and stable group ids make a retry safe. Quality in production is judged by reviewer accept/reject rates, which are the signal we would monitor. |
| **Performance efficiency** | Grouping before any model call is the single biggest lever: 59 questions become ~12 groups. Retrieval returns passages, not documents, so prompt size stays bounded. The slow part will be the model calls, measured per group from the callback timings. Latency is not a constraint — nothing waits on this; the figure that matters is a day's questions inside an overnight window. |
| **Cost effectiveness** | Grouping is deterministic Python, not a model call — the clearest case of moving undifferentiated work off the model. Triage short-circuits duplicates and refusals before retrieval and drafting, so roughly half the log never reaches the expensive steps. Token counts are logged per call so the deck can quote worst-case cost per batch, not a flattering average. |
| **Operational excellence** | Every model and tool call is logged with latency and tokens, and the passages behind each draft are recorded — that is what makes approval real rather than ceremonial. The eval set is the regression gate. Recovery is simply re-running the batch; the whole environment rebuilds from the committed generator. Known limitation for handover: the corpus is synthetic, so the eval set proves behaviour against fixtures, not real content. |
| **Deployment** | Google Cloud, as a design question — nothing deployed live. A scheduled overnight job suits this better than a service: no request path, no scaling pressure, failure delays a draft and degrades nothing a user sees. Agent Engine or a Cloud Run job, fixtures as read-only assets, secrets in Secret Manager, traces to Cloud Trace, the eval suite as a build-time gate. The queue file is the integration point and it is human-operated. |
