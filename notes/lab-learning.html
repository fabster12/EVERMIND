2. Greenfield and Brownfield

  • Greenfield: Build a new application. Start with a validated problem, users, explicit requirements, synthetic data, and narrowly scoped interfaces. There is no existing project codebase to preserve.
  • Brownfield: Modify an existing application. First establish its architecture, business rules, tests, ownership, integration contracts, and migration constraints. Preserve current behavior unless a change is intentional.
  • These skills support either approach. The FedEx proposals below are greenfield only because no existing internal project, architecture, or authorized integration has been identified. An idea may overlap an existing tool; stakeholder discovery must check that before investment.

Evidence That You Can Reuse the Skills

  • For the first-agent and tools labs: explain one invocation from request to events, tool result, and answer; show which code actually authorizes and executes the tool.
  • For classification and workflows: demonstrate a schema-valid result, a validation/error path, an uncertain result, and bounded recovery. A model's self-reported confidence is not a calibrated probability of correctness.
  • For guardrails: show both unchanged and intercepted paths, including tool-call steps and combined-plugin/cache-hit behavior. Count actual model invocations separately from before-hook entries.
  • For tests and evaluations: keep deterministic test results separate from model-quality scores. Record model, prompt, tool, policy, and evaluation-set versions so a later change can be compared fairly.
  • For deployment: demonstrate endpoint access, traces, failure handling, and usage accounting. A local demo or walkthrough is not evidence that a cloud deployment has been completed.

Compatibility checkpoint: The lesson guide explicitly cautions that combining output_schema with tools depends on model support. Do not assume that one tool-using agent can also enforce the chosen output schema on every backend. Verify the exact provider/model/SDK combination, or retrieve facts in application code and pass them to a separate schema-output step. See the model-support caveat.

What the Current Plugins Lab Actually Demonstrates

The current lab provides a useful capstone pattern: one agent answers order-status questions, agent-local callbacks handle selected input/output checks, and application-wide plugins provide logging, caching, or response intervention.

  • Returning a response from a before-model hook can skip the model call. Returning None allows that hook to leave normal execution unchanged.
  • An after-model hook can replace a response, but replacing a short answer is not a retry and not a factual-quality check.
  • Logs make hook execution observable. A before-model log does not by itself prove that a paid model request occurred: a later hook may short-circuit it. Logs also need redaction and access controls; tool arguments can themselves contain sensitive information.
  • Multiple configured plugins are not proof that every hook runs on every path. Verify ordering, early returns, cache hits, and guardrail interactions in the installed SDK.

7. Recommended Capstone: Shipment Exception Triage Assistant

Problem and Users

Hypothesis: A support or operations analyst can review a defined shipment exception more consistently when shipment facts and the relevant procedure are assembled into one evidence-backed draft.

Primary user: A human reviewer. Decision boundary: The assistant summarizes and recommends; the reviewer decides. It must not invent delivery commitments or autonomously change shipment instructions.

Start with one stakeholder-approved exception category, one operating-policy set, and one synthetic data format. Confirm that this is not duplicating an existing capability before expanding it.

First Demonstration Before a Full MVP

Build one vertical slice: a synthetic case goes in; a validated, evidence-backed draft comes out; a person accepts, edits, or rejects it. A command-line or small local page is enough initially. A queue, cloud deployment, MCP server, A2A team, and response cache are not prerequisites.

Use this separation of responsibilities:

  1. Application code validates the case and retrieves the allowed snapshot and policy.
  2. Deterministic code prepares the timeline and identifies missing/contradictory data without inventing facts.
  3. One schema-output model step interprets the permitted text and drafts a supported explanation.
  4. Application code validates fields and reference IDs; a reviewer checks whether the cited sources actually support the claims.
  5. The application records the reviewed result and the input/model/policy versions used.

This avoids assuming simultaneous tool use and schema output. Later, introduce a tool-selecting agent only if the retrieval sequence genuinely needs dynamic decisions and the backend supports the intended contract.

A Concrete Synthetic Case

This is invented demonstration data, not a real shipment, tracking-number format, FedEx procedure, or delivery-service rule.

ItemDemonstration value
CaseSIM-1001; customer text: "Has this shipment been delivered?"
SnapshotRetrieved at 2026-10-14T12:00:00Z; contains event E-101 (received at origin) and E-102 (in transit), each with its own event timestamp. No delivery event is supplied.
Fictional policyP-DEMO-01: state only what the supplied evidence supports; request a refreshed authoritative snapshot when delivery cannot be confirmed.
Expected classificationinsufficient_delivery_evidence, under the prototype's explicitly defined categories. It is not automatically a delay or lost-shipment classification.
Supported draft"The supplied snapshot's latest event is in transit. Delivery cannot be confirmed from this snapshot." Cite E-102 and the snapshot retrieval time.
Reviewable next stepRequest or review a refreshed authoritative tracking snapshot, following P-DEMO-01; make no operational change.

The paired test adds a later delivery event to a new snapshot and checks that the draft changes appropriately. A second test keeps the same customer wording but uses a different case: facts must not be copied across cases. These tests make freshness and evidence boundaries observable.

MVP Scope

  • Input: a synthetic shipment identifier, timestamped scan/event history, an optional customer message, and a small approved or explicitly fictional policy set.
  • Tools: read-only shipment lookup and policy lookup through mock adapters. Return typed data, source identifiers, timestamps, and explicit error states.
  • Processing: deterministic code validates identifiers and prepares events under specified timestamp/time-zone rules; a schema-output step classifies/summarizes only the supplied facts. Missing, stale, or contradictory evidence produces an unknown/review-required result. Preserve event time and snapshot retrieval time as different fields.
  • Output: a structured issue category, factual timeline, supporting event/policy references, a draft next action, uncertainty reasons, and a human-review flag. A schema-valid answer still requires factual checks.
  • Workflow: validate/authorize input -> retrieve facts -> classify and draft -> validate output/references -> human review of evidence and recommendation -> record the review outcome. A valid reference ID alone does not prove a supported claim.
  • UI after the first slice: a compact review queue and case detail view showing facts, references, and the draft. The user can accept, edit, or reject the recommendation; save decisions only within the prototype. Track reviewer identity, outcome, corrections, and the original draft; do not silently overwrite the audit trail.
  • Out of scope: automatic rerouting, automatic refunds, operational shipment updates, real customer messaging, customs/legal determinations, and predicted delivery dates without an authoritative source.

Milestones

  1. Discover and specify: Confirm the target reviewer, exception category, data boundaries, and success criteria. Write proposal, scenarios, design, and tasks. No operational integration yet.
  2. Build the deterministic baseline: Create synthetic fixtures, read-only adapters, event validation, and a simple fact/template view. Establish what works without an LLM; use it as the comparison, not just a preparatory step.
  3. Add one validated ADK model step: Add structured classification and evidence-backed draft summaries. Check backend/schema compatibility and add logging, fallback, and input/output controls. Do not add dynamic tool selection, multi-agent/A2A, or caching by default.
  4. Verify: Test error paths, isolation, prompt injection, unsupported claims, and plugin combinations. Run a held-out evaluation set and compare the assistant with the deterministic baseline.
  5. Demonstrate and hand over: Deliver a local demo, test/evaluation report, trace/cost examples, limitations, and updated specs. A cloud pilot is optional and requires approval, access, and budget.

Suggested Acceptance Gates

These are proposed capstone gates, not measured results or guaranteed production outcomes. Agree the exact thresholds with the sponsor.

AreaProposed verification
Deterministic correctnessAll agreed tests pass for identifiers, event ordering, missing data, service failures, and review transitions.
Structured outputEvery evaluated final output either conforms to the schema or produces a controlled fallback; no unhandled parse failures. Report fallback/abstention rate separately so a system that refuses every case cannot appear useful.
Factual groundingOn the held-out set, each asserted shipment fact has a valid reference whose content actually supports the assertion, checked against labeled facts or by a reviewer. Unsupported ETAs, fabricated events, and unsupported "not delivered" claims fail the gate.
Safety and isolationAll defined authorization, cross-user/cache-isolation, and prohibited-write test cases pass. This is evidence for those cases, not proof against every possible attack.
Useful triageA domain reviewer labels category and next-step usefulness on held-out cases. Report errors per category, unknown handling, and coverage, not just one overall accuracy score. Choose a target after establishing the baseline and class balance.
Operational valueCompare review time and correction rate with the deterministic/template baseline on the same cases; counterbalance case order to reduce practice effects. A claim about FedEx's actual workflow requires a separate authorized study against that workflow. Do not promise a percentage before measurement.
Cost and observabilityRecord model/tool calls, latency, token use or available cost estimates, fallback count, and intervention count, without leaking sensitive data.

Size the synthetic fixture set to cover the agreed scenarios rather than targeting an arbitrary number. Include normal cases, unknown identifiers, incomplete/out-of-order scans, conflicting timestamps, tool failures, missing policies, injection attempts, and repeated queries after facts change. Split development and held-out cases by underlying shipment/scenario family, not just by paraphrasing the same example. Freeze the held-out set before tuning; do not count it as held-out after using its failures to tune the system.

Run repeated model evaluations with recorded settings to expose variability. Use domain labels as the main reference; LLM-as-judge scores are supporting signals, not the sole release authority. Synthetic results demonstrate the prototype, not real-world FedEx effectiveness or a statistically established safety rate.

Definition of Done for the Local Capstone

  • A fresh checkout can run with documented dependencies and synthetic fixtures, without requiring operational credentials. Live model access, if used, must be approved; deterministic tests work without it.
  • The demonstration includes one normal case, one uncertain case, one tool/service failure, one adversarial-input case, and one changed-snapshot case.
  • Each accepted requirement links to verification evidence. Keep mock-test results separate from live-model evaluation results and identify any checks that were not run.
  • The handover includes the brief, specs/design/tasks, reviewed implementation, setup/demo instructions, evaluation dataset/version, results, limitations, and sample redacted traces.
  • The deterministic baseline comparison shows where the model helps and where it does not. If there is no demonstrated improvement, retain the simpler baseline rather than forcing an agent into the solution.

Security and Production Boundaries

  • Start with synthetic or explicitly approved de-identified data. Do not upload operational/customer data, internal policies, or credentials to an unapproved model service.
  • Enforce identity and permissions in the service/tool layer. A prompt, Copilot instruction, or MCP description is not an access-control boundary.
  • Avoid caching mutable shipment answers in the MVP. If caching is later added, use scoped keys, versioning, freshness rules, and cache-hit safety tests; do not copy the lab's latest-text-only cache into production.
  • Keep operational writes outside the prototype. Any future write capability needs authorization, human approval where appropriate, idempotency, auditability, and rollback/recovery design.
  • Treat tool results and documents as untrusted content. Require provenance; test malicious embedded instructions and failures explicitly.
  • Store secrets outside source control and reports. Use approved secret management for a hosted pilot; never put keys into logs or prompts.

Important Gaps Beyond These Labs

The labs introduce patterns; they do not establish a complete enterprise delivery capability. A real pilot may additionally need identity/tenant isolation, persistence and migrations, retention and deletion rules, approved integration contracts, policy ownership/versioning, OCR or retrieval infrastructure, load/concurrency testing, threat modeling, operational monitoring, and support ownership. Treat these as separately scoped engineering work, not capabilities automatically acquired by completing a lab.

For a future brownfield capstone, add a characterization-test baseline, existing API/data contracts, and a rollout/rollback or migration plan before changing behavior. Do not infer an existing project's rules from the sample ticket, order, or coffee application.

8. A Reusable Planning Checklist

For either a future greenfield or brownfield project, record the following before implementation:

  1. The user, task, problem hypothesis, and current baseline.
  2. Inputs, outputs, data classification, authoritative sources, and tool permissions.
  3. Scope and exclusions; existing code/integration constraints for brownfield work.
