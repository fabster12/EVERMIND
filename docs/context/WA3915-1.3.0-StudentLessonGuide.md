### 1.4. What Is an AI Agent?

An **AI agent** is a large language model paired with the surrounding machinery that lets it act.

  * **Model** : a large language model that produces text and reasoning

  * **Tools** : functions the model can invoke to look up data, call APIs, or take action

  * **Sessions and memory** : conversation history, working state, and durable long-term knowledge

  * **Runtime** : code that runs the model, dispatches tool calls, and decides when the task is done

#### 1.4.1. A Direct Call vs. an Agent

**A direct model call**

  * Answers a single question

  * No tools, no state

  * One request, one response

**An agent**

  * Decomposes a task into steps

  * Calls tools to gather data or act

  * Tracks state and continues until the goal is met

### 1.5. What Is the Agent Development Kit?

The **Agent Development Kit (ADK)** is Google’s open-source framework for building, running, evaluating, and deploying AI agents.

**What ADK Provides**

  * A typed agent model and a managed runtime

  * Tools, sessions, memory, and streaming

  * Workflow and multi-agent orchestration

  * Evaluation, observability, and deployment

**Why It Matters**

  * One framework from prototype to production

  * Model-flexible: Gemini and external models

  * Built-in guardrails and evaluation

  * Managed deployment on Google Cloud

ADK is model-flexible: an ADK agent runs on a Gemini model by default, and the same agent can run on an external or locally hosted model through a connector. The course uses Gemini as the default and shows how to swap backends. This course targets ADK 2.0, the general-availability release that introduced graph-based workflows and collaborative agents. The course builds the full picture incrementally: the first three modules introduce agents, structured outputs, and tools; the middle modules add state, memory, callbacks, and evaluation; the final modules cover orchestration, multi-agent systems, and production deployment.

### 2.3. The ADK Runtime Model

ADK separates **what an agent is** from **how it runs**. You define an agent declaratively; the runtime executes it.

#### 2.3.1. The Core Primitives

Primitive | Role  
---|---  
Agent | The model, instructions, and tools: what to do  
Runner | Orchestrates execution and commits results  
Session | One conversation thread, its events, and its state  
Event | A single step: a message, a tool call, or a result  
  
#### 2.3.2. The Event Loop

  * The runner sends the user message to the agent

  * The agent runs the model and produces an event

  * The agent yields the event and pauses

  * The runner commits state, then resumes the agent

  * The loop repeats until no events remain

#### 2.3.3. The Yield-and-Commit Cycle

#### 2.3.4. One Invocation, End to End

#### 2.3.5. Invocations, Events, and State

  * An **invocation** is one user input to final output

  * Each invocation produces one or more **events**

  * Events carry content and state changes

  * The **session** accumulates events across turns

  * State is the agent’s working memory within a session

### 2.4. Creating a Basic Agent

The fastest way to start a project is the `adk create` command, which scaffolds a working agent.

#### 2.4.1. Scaffolding a Project
    
    
    adk create my_agent

This creates a small project:
    
    
    my_agent/
        __init__.py     # exposes the agent package
        agent.py        # defines root_agent
        .env            # API keys and project settings

#### 2.4.2. The Root Agent

  * `agent.py` must define a variable named `root_agent`

  * The adk tooling locates the agent by that name

  * `root_agent` is the entry point for every run

  * A multi-agent project still has one `root_agent`

#### 2.4.3. The LlmAgent Class

The `LlmAgent` class (often written simply as `Agent`) defines a model-driven agent.
    
    
    from google.adk.agents import LlmAgent
    
    root_agent = LlmAgent(
        name="time_assistant",
        model="gemini-flash-latest",
        description="Reports the current time in a city.",
        instruction="You are a helpful assistant. Use the "
                    "get_current_time tool to answer time questions.",
        tools=[get_current_time],
    )

#### 2.4.4. The Core Parameters

Parameter | Purpose  
---|---  
`name` | A unique identifier for the agent  
`model` | The model the agent runs on  
`description` | How other agents decide to delegate to this one  
`instruction` | The agent’s role and behavior (its most important field)  
`tools` | The functions the agent may call  
  
The `description` field matters only in multi-agent systems: a coordinator agent reads the `description` of each candidate sub-agent to decide where to route a request. For a single agent it can be brief. The `instruction` field, by contrast, is always load-bearing: it is the agent’s standing brief, covered in detail later in this module.

### 2.5. ADK Project Structure

A well-organized project makes agents easier to run, test, and extend. ADK’s tooling has strong opinions about the entry point name.

#### 2.5.1. The Single-Agent Layout
    
    
    my-agent/                   ← the project root (run uv sync here)
        my_agent/               ← the Python package
            __init__.py         ← marks this as a package
            agent.py            ← defines root_agent
            tools.py            ← tool functions, one module per concern
        tests/
            test_agent.py
        pyproject.toml
        .python-version
        .env                    ← API keys; never commit this file

#### 2.5.2. The `root_agent` Contract

  * `adk run` and `adk web` discover the agent by scanning for a variable named `root_agent`

  * The name is mandatory: a missing or misspelled variable causes a silent discovery failure

  * Every project has exactly one `root_agent`; sub-agents are registered on it, not exported separately

#### 2.5.3. Tool Schema Is Auto-Generated

ADK builds each tool’s JSON schema from three sources. All three are load-bearing.

Source | What it controls  
---|---  
Function name | The name the model sees; make it a clear verb phrase  
Docstring | The description the model reads to decide when to call the tool  
Type hints and defaults | Parameter types, required vs. optional, and default values  
  
A missing docstring or type hint is the single most common reason a tool is never called.

#### 2.5.4. The Most Common Setup Mistake

Running `uv sync` from the wrong directory creates a venv in the wrong place.
    
    
    # Wrong — creates .venv/ inside the package subdirectory
    cd my-agent/my_agent
    uv sync          # will not find pyproject.toml
    
    # Correct — creates .venv/ beside pyproject.toml
    cd my-agent
    uv sync
    uv run adk web

Always run `uv sync` and `uv run` from the project root, where `pyproject.toml` lives.

### 2.7. Agent Instructions

The `instruction` is the agent’s standing brief. ADK supports three forms, from simplest to most dynamic.

#### 2.7.1. Static Instructions

A constant string. Use it when behavior never changes.
    
    
    instruction=(
        "You are a support assistant for an online store. "
        "Answer questions about orders politely and concisely."
    )

#### 2.7.2. State-Templated Instructions

A string with `{placeholder}` markers that ADK fills from session state.
    
    
    instruction=(
        "You are assisting {user:name}. "
        "Their support tier is {user:tier}."
    )

  * `{key}` inserts a value from session state

  * `{key?}` is optional; a missing value is left blank

  * A missing `{key}` without `?` raises an error

#### 2.7.3. Dynamic Instructions

A function that builds the instruction at run time.
    
    
    def build_instruction(context) -> str:
        return (
            "You are a support assistant. "
            f"Today's date is {today()}."
        )
    
    root_agent = LlmAgent(
        name="support",
        model="gemini-flash-latest",
        instruction=build_instruction,
    )

#### 2.7.4. Choosing an Instruction Form

Form | Use when  
---|---  
Static | Behavior is fixed  
State-templated | Behavior depends on stored session values  
Dynamic | Behavior depends on computed or live data  
  
A fourth field, `global_instruction`, is set on the root agent of a multi-agent system and applies to every agent beneath it. Use it for guidance that all agents in a system share (a tone of voice, a safety rule, a company name) and keep each agent’s own `instruction` focused on that agent’s specific job. Multi-agent systems are covered later in the course.

### 2.8. Configuring Model Backends

An ADK agent is not tied to one model. The `model` parameter selects the backend.

#### 2.8.1. Gemini Models

  * Pass the Gemini model name as a string

  * ADK resolves it to the right client

  * The course default is a Gemini Flash model

  * Flash models are fast and cost-efficient

    
    
    root_agent = LlmAgent(
        name="assistant",
        model="gemini-flash-latest",
        instruction="You are a helpful assistant.",
    )

#### 2.8.2. External Models with LiteLlm

The `LiteLlm` connector runs an agent on a non-Gemini model.
    
    
    from google.adk.models.lite_llm import LiteLlm
    
    root_agent = LlmAgent(
        name="assistant",
        model=LiteLlm(model="openai/gpt-5.5"),
        instruction="You are a helpful assistant.",
    )

  * Wrap the model name in a `LiteLlm` object

  * Use the `provider/model` naming format

  * Provider API keys come from environment variables

  * The same agent code works on either backend

#### 2.8.3. Generation Settings

Control how the model generates text with a generation config.
    
    
    from google.genai import types
    
    root_agent = LlmAgent(
        name="assistant",
        model="gemini-flash-latest",
        instruction="You are a helpful assistant.",
        generate_content_config=types.GenerateContentConfig(
            temperature=0.2,
            max_output_tokens=1024,
        ),
    )

  * `temperature` controls randomness

  * `max_output_tokens` caps the response length

### 2.9. Synchronous and Asynchronous Execution

When you run an agent from your own code rather than the CLI, you use a `Runner`.

#### 2.9.1. Setting Up the Runner and Session

Create a session service, wrap the agent in a `Runner`, and open a session.
    
    
    from google.adk.runners import Runner
    from google.adk.sessions import InMemorySessionService
    from google.genai import types
    
    session_service = InMemorySessionService()
    runner = Runner(
        agent=root_agent,
        app_name="demo",
        session_service=session_service,
    )
    await session_service.create_session(
        app_name="demo", user_id="user1", session_id="s1")

#### 2.9.2. Walking the Events

Build a message, then walk the events the invocation produces.
    
    
    message = types.Content(
        role="user", parts=[types.Part(text="Hello")])
    
    async for event in runner.run_async(
        user_id="user1", session_id="s1", new_message=message):
        if event.is_final_response():
            print(event.content.parts[0].text)

#### 2.9.3. Async Is the Primary Model

  * `run_async` is ADK’s primary execution method

  * It yields events as the agent produces them

  * `async for` walks the events of one invocation

  * `is_final_response()` marks the agent’s answer

#### 2.9.4. Blocking versus Event Stream

#### 2.9.5. When to Use Which

Reach for the CLI (`adk run`, `adk web`) | Reach for `runner.run_async`  
---|---  
Quick manual checks while developing | Embedding the agent in your own application  
Interactive exploration during development | Reacting to events as they arrive: streaming, logging  
One-off questions, demos | Tests, scripts, and anything automated  
  
The rule of thumb: the CLI is for **you** , the Runner is for **your code**. Every production path (a web backend, a test suite, a batch job) drives the agent through `run_async`, which is why the labs practice it early. The CLI remains the fastest way to poke at an agent while you build it.

#### 2.9.6. Streaming Partial Events

  * Long responses arrive as a series of events

  * Partial events carry text as it is generated

  * Streaming reduces the wait a user perceives

  * Running interactively shows partial events as they arrive

### 3.2. Why Structured Outputs Matter

A model returns text. An application needs data.

  * Free-form text is easy for people to read

  * It is hard for code to consume reliably

  * Parsing prose with string matching is fragile

  * Structured output gives code a stable contract

#### 3.2.1. The Problem with Free-Form Text

Ask a model to classify a document and it might answer:

This looks like an invoice to me - I’d say I’m fairly confident.

  * Which field is the category?

  * How confident is "fairly confident" as a number?

  * The wording changes every run

#### 3.2.2. The Value of a Schema

A **schema** is a typed description of the data you expect.

**Free-form text**

  * Shape changes every run

  * Needs fragile parsing

  * No guarantees

**Schema-constrained output**

  * Same fields every run

  * Parsed into typed objects

  * Validated automatically

### 3.3. Defining Schemas with Pydantic

ADK uses **Pydantic** models to describe structured data. A Pydantic model is a Python class whose typed attributes define the fields.

#### 3.3.1. A Pydantic Model
    
    
    from pydantic import BaseModel
    
    
    class Classification(BaseModel):
        category: str
        confidence: float
        summary: str

  * Each attribute is a field with a type

  * Pydantic validates values against those types

  * The model is both the schema and the parsed result

#### 3.3.2. Field Constraints

The `Field` function adds constraints to a field.
    
    
    from pydantic import BaseModel, Field
    
    
    class Classification(BaseModel):
        category: str
        confidence: float = Field(ge=0.0, le=1.0)
        summary: str = Field(min_length=1, max_length=200)

  * `ge` and `le` bound a number

  * `min_length` and `max_length` bound text

  * A value outside the bounds fails validation

#### 3.3.3. Input and Output Schemas

An `LlmAgent` accepts a schema on either side.

Parameter | Effect  
---|---  
`input_schema` | The user message must match this schema  
`output_schema` | The agent’s final response must match this schema  
  
Most agents in this course use `output_schema`; the common need is a reliable, typed **result**. Use `input_schema` when an agent is an internal step in a larger system and its caller is code rather than a person, so the incoming message is itself a structured object. The two parameters are independent; an agent can set either, both, or neither.

### 3.4. Constraining Responses with output_schema

Setting `output_schema` on an agent constrains its final response to that schema.
    
    
    from google.adk.agents import LlmAgent
    
    classifier = LlmAgent(
        name="doc_classifier",
        model="gemini-flash-latest",
        instruction="Classify the document the user provides.",
        output_schema=Classification,
    )

  * The agent’s final response conforms to `Classification`

  * ADK constrains the model output to match the schema (delivered as a JSON string that you load into the Pydantic model)

  * Every run returns the same fields with the same types

#### 3.4.1. What the Agent Returns

**Without a schema**

  * A paragraph of text

  * Shape varies every run

  * Code must parse prose

**With a schema**

  * A `Classification` object

  * `category`, `confidence`, `summary` always present

  * Code reads fields, not prose

### 3.5. Validators for Business Rules

Type and range constraints are not always enough. A **validator** enforces rules that types cannot express.

#### 3.5.1. Field Validators
    
    
    CATEGORIES = ["invoice", "support_ticket", "product_review"]
    
    class Classification(BaseModel):
        category: str
    
        @field_validator("category")
        @classmethod
        def category_must_be_known(cls, value: str) -> str:
            normalized = value.strip().lower()
            if normalized not in CATEGORIES:
                raise ValueError(f"unknown category: {value}")
            return normalized

#### 3.5.2. What Validators Are For

  * Restrict a value to an allowed set

  * Normalize a value (trim spaces, fix case)

  * Enforce relationships between fields

  * Reject output that is typed correctly but wrong

### 3.6. Handling Validation Failures

A model can produce output that does not satisfy the schema. Plan for it.

#### 3.6.1. When Output Fails Validation

  * The model returns a value out of range

  * A required field is missing

  * A validator rejects a business-rule violation

  * Validation raises an error instead of returning data

#### 3.6.2. Automatic Retries in ADK 2.0

  * ADK 2.0 can catch failures and retry a step

  * A `RetryConfig` sets how many attempts to make

  * Let unexpected errors propagate so retries can fire

  * Do not wrap agent or tool code in broad error handling

    
    
    from google.adk.workflow import RetryConfig
    
    classifier = LlmAgent(
        name="doc_classifier",
        model="gemini-flash-latest",
        output_schema=Classification,
        retry_config=RetryConfig(max_attempts=3),
    )

#### 3.6.3. Designing a Fallback

When retries are exhausted, fail gracefully.

  * Return a safe default result

  * Mark the result as low-confidence or "unknown"

  * Record the failure for later review

  * Never crash the caller with an unhandled error

    
    
    # retries exhausted -> return a safe default instead of raising
    try:
        result = run_classifier(document)
    except ValidationError:
        result = Classification(category="unknown", confidence=0.0)
        log_for_review(document)

### 3.7. Schema-Constrained Output versus Tool-Using Output

There are two ways an agent can produce structured data.

**Schema-constrained**

  * Set `output_schema`

  * The model fills the schema directly

  * Best for a pure transformation

**Tool-using**

  * The agent calls tools

  * A tool returns structured data

  * Best when the agent must act first

#### 3.7.1. The Model-Support Caveat

  * Combining `output_schema` with `tools` is limited

  * Only some models support both at once

  * For others, the combination is unreliable

  * Plan the agent’s design around this limit

#### 3.7.2. Splitting Work Across Agents

When an agent needs both tools and a strict output shape, split the work.

  * One agent uses tools to gather information

  * A second agent formats the result with `output_schema`

  * Each agent does one job well

### 3.8. Multi-Format Responses with Union Schemas

Sometimes one agent must return one of several shapes.

  * Pydantic supports union types that allow more than one result shape

  * Whether the model reliably picks the right variant depends on the model and provider

  * Each shape is its own validated model

  * Specialized agents can handle each shape

A union output is useful when a single entry point handles mixed input. For example, a document agent that returns an `InvoiceData` object for an invoice and a `TicketData` object for a support ticket. An alternative design routes the request to a specialized agent for each type, so each agent has one simple schema. The course lab explores the routing approach, which keeps each schema small and each agent focused.

### 3.9. Capturing Results with Named Result Keys

A structured result is most useful when later steps can read it.

#### 3.9.1. The output_key Parameter
    
    
    classifier = LlmAgent(
        name="doc_classifier",
        model="gemini-flash-latest",
        instruction="Classify the document the user provides.",
        output_schema=Classification,
        output_key="classification",
    )

  * `output_key` names a slot in session state

  * The agent’s final response is written there

  * With an `output_schema`, the stored value is the JSON string; downstream code loads it into the Pydantic model

  * Later agents and tools can read that value

  * This is how a pipeline passes data between steps

#### 3.9.2. Results Flow Through State

  * Step one writes a result under its `output_key`

  * Session state holds the value across the run

  * Step two reads it from state

  * Structured results become a shared contract

### 5.2. What a Token Costs

A token is roughly four characters of English text. Pricing reflects the direction of flow.

Token type | Notes  
---|---  
Input tokens | Everything sent to the model: system prompt, conversation history, tool definitions, tool results  
Output tokens | Everything the model generates: text responses and function calls; priced higher than input  
Cached tokens | Input tokens served from the prompt cache; charged at a fraction of the regular input rate  
  
#### 5.2.1. Why Output Costs More

  * The model generates output tokens one at a time, which is compute-intensive

  * Input tokens are processed in parallel — more efficient per token

  * A typical agent run is read-heavy (many input tokens) and write-light (fewer output tokens)

  * `output_schema` enforces a fixed response shape, which reduces output token variance

#### 5.2.2. Prompt Caching

  * Gemini caches the prefix of a prompt automatically when a request qualifies

  * Cached tokens are billed at roughly one quarter the standard input rate

  * Caching helps most when a large system prompt or tool list is reused across many turns

  * Context that changes every turn (conversation history) does not benefit from caching

### 5.3. The Gemini Model Landscape

Google publishes a family of models with different speed-cost-capability profiles.

Model family | Best for | Watch out for  
---|---|---  
Flash | Most agent tasks; fast and inexpensive; the right default | May need Pro for complex multi-step reasoning or very long context  
Flash-Lite | High-volume, low-complexity classification and extraction | Weaker reasoning; test carefully before deploying to production workloads  
Pro | Tasks where Flash demonstrably fails; long-context synthesis; complex chain-of-thought | Slower and more expensive; use only when Flash cannot do the job  
  
#### 5.3.1. The Model Selection Rule of Thumb

Start with Flash. Upgrade only when Flash fails on the task.

A model swap in ADK is one line:
    
    
    root_agent = LlmAgent(
        name="assistant",
        model=os.getenv("ADK_MODEL", "gemini-flash-latest"),
        ...
    )

By reading the model from an environment variable, you switch between Flash and Pro by changing `.env` — no code change required.

#### 5.3.2. `output_schema` Reduces Output Token Variance

A free-text response can range from 10 tokens to 2,000 tokens depending on how verbose the model feels. A structured output schema caps the shape of the response.

  * `output_schema` forces the model to emit valid JSON matching the Pydantic model

  * Structured JSON is more compact than prose for the same information

  * Lower variance makes cost predictions more reliable

  * Combine with `max_output_tokens` in `GenerateContentConfig` for a hard ceiling

### 5.4. The Biggest Cost Lever: Context

Every token in the context window is a token you pay for. The context window is not just the user message.

#### 5.4.1. What Goes Into the Context Window

Component | Notes  
---|---  
System prompt | The agent’s instruction; present on every turn; often the largest single item  
Tool definitions | One JSON schema per tool; a ten-tool agent adds significant input overhead every turn  
Conversation history | All prior messages in the session; grows with every turn  
Tool results | The dict each tool returns; a tool that returns a 10,000-character file adds that to context  
  
#### 5.4.2. How Tool Calls Compound

Each round trip between the model and a tool adds tokens on both sides.

  * Every function call costs output tokens (the call itself) and input tokens (the result)

  * An agent that calls three tools per turn may generate five or more billable model steps

  * Fewer, better tools reduce round trips

#### 5.4.3. Design for Fewer Round Trips

Instead of | Prefer  
---|---  
Many narrow tools (one API call per tool) | Fewer, composable tools that return richer results  
A tool that returns raw API JSON | A tool that extracts and returns only the fields the model needs  
Splitting a workflow across many agent turns | A single tool call that does the batch work  
  
The principle: keep undifferentiated work out of the model’s hands. If a sequence of steps is always the same, run it in a Python function and return the result as a single tool response.

### 5.5. Monitoring and Right-Sizing

Before you can cut costs you need to see where they come from.

#### 5.5.1. Google AI Studio Usage Dashboard

  * Available at [aistudio.google.com](https://aistudio.google.com/) under **Settings → API usage**

  * Shows per-model, per-day token counts and request volumes

#### 5.5.2. ADK Dev UI Traces Tab

  * Cloud Monitoring dashboards can track custom metrics emitted via OpenTelemetry

#### 5.5.4. The Right-Sizing Heuristic

Ask this question for each component of cost: **is the model doing work that my code could do instead?**

  * Summarizing a thousand-line file: could a Python excerpt replace a raw-file tool result?

  * Routing between two code paths: could a conditional in `before_agent_callback` replace a model call?

Every "yes" answer is an opportunity to cut cost and latency at the same time.

### 6.2. Defining Success Criteria for Agent Outputs

Criterion | The question it answers  
---|---  
Accuracy | Is the answer factually correct?

Format | Is it shaped the way a downstream consumer expects?  
Safety | Does it stay within policy (no disallowed or harmful content)?  
  
### 6.3. The Callback Lifecycle

A **callback** is a function ADK runs at a fixed point in an agent’s execution. Callbacks let you inspect, log, or change what happens without editing the agent’s core logic.

#### 6.3.1. Three Boundaries, Two Hooks Each

Boundary | Before / after hooks  
---|---  
Agent | `before_agent_callback`, `after_agent_callback`  
Model | `before_model_callback`, `after_model_callback`  
Tool | `before_tool_callback`, `after_tool_callback`  
  
  * A **before** hook runs just ahead of the step

  * An **after** hook runs just behind it

  * Callbacks are configured per agent, for example: `before_model_callback=my_function`

#### 6.3.2. Hooks Wrap Each Step

#### 6.3.3. Where the Hooks Fire

  * Each **before** hook can skip its step; each **after** hook can replace its result

  * `before_model`/`after_model` and `before_tool`/`after_tool` fire **per iteration**. An agent run may loop through model and tool calls several times (or call no tools at all) before reaching `after_agent`

#### 6.3.4. The Return Value Controls the Step

The value a callback returns decides what happens next.

Returns | Effect  
---|---  
`None` | The step proceeds normally  
A value | The step is skipped or its result replaced  
  
  * A `before_model_callback` that returns an `LlmResponse` **skips** the model call

  * An `after_model_callback` that returns an `LlmResponse` **replaces** the model’s answer

  * A `before_tool_callback` that returns a dict **skips** the tool; the dict is treated as the tool’s result

  * This is the mechanism behind every guardrail in this module

Returning a value from a callback is a deliberate override, not an error path. A `before` callback that returns a value is saying "I have already produced the result for this step; do not run it." An `after` callback that returns a value is saying "replace what just happened with this." Returning `None` is the common case and means "carry on." Keep callbacks fast and side-effect-light; they run on every matching step.

#### 6.3.5. A Guardrail Callback in Practice

The `block_injection` callback is an input guardrail: it returns an `LlmResponse` to skip the model when the input looks like a prompt injection, and `None` to let a normal request through.
    
    
    def block_injection(callback_context, llm_request):
        """Skips the model when the input looks like a prompt injection."""
        last = llm_request.contents[-1] if llm_request.contents else None
        text = last.parts[0].text if last and last.parts else ""
        if "ignore previous instructions" in text.lower():
            return LlmResponse(
                content=types.Content(
                    role="model",
                    parts=[types.Part(text="That request can't be processed.")],
                )
            )
        return None  # let the model run

### 6.4. Plugins: Process-Wide Behavior

A callback is scoped to one agent. A **plugin** applies its hooks to **every** agent, model, and tool in a run.

#### 6.4.1. Defining and Registering a Plugin

  * A plugin subclasses `BasePlugin` and overrides the hooks it needs

  * The same six before/after hooks are available, plus run-level hooks

  * A plugin is registered once, on an `App`, not on an agent

  * The `App` is then handed to the `Runner`

#### 6.4.2. A Plugin, Defined and Registered
    
    
    from google.adk.apps import App
    from google.adk.plugins.base_plugin import BasePlugin
    from google.adk.tools.base_tool import BaseTool
    from google.adk.tools.tool_context import ToolContext
    
    class LoggingPlugin(BasePlugin):
        async def before_tool_callback(
            self, *, tool: BaseTool, tool_args: dict, tool_context: ToolContext
        ):
            print(f"[plugin] tool call: {tool.name}({tool_args})")
            return None
    
    app = App(name="app", root_agent=root_agent, plugins=[LoggingPlugin()])
    runner = InMemoryRunner(app=app)

#### 6.4.3. Plugin Hooks Run Before Agent Callbacks

  * For a given step, the plugin hook fires **first**

  * Then the matching agent callback fires

  * So a plugin can short-circuit a step before any agent ever sees it

  * That ordering is what makes plugins the right home for cross-cutting policy

#### 6.4.4. Three Ways a Plugin Acts

**Observe**

  * Read and record

  * Logging, metrics, tracing

  * Returns `None`: leaves everything unchanged

**Intervene**

  * Short-circuit a step

  * Return a value from a **before** hook

  * Caching, guardrails

**Amend**

  * Adjust a result

  * Return a value from an **after** hook

  * Sanitizing, quality gates

#### 6.4.5. When to Use Which

Use a…​ | When the logic is…​  
---|---  
Callback | Specific to one agent  
Plugin | Cross-cutting: logging, caching, and security across the whole run  
  
### 6.5. Input and Output Guardrails

A **guardrail** is a policy check enforced with a callback or plugin.

Guardrail | How it is built  
---|---  
Input guardrail | A `before_model_callback` that inspects the request and can skip the model  
Output guardrail | An `after_model_callback` that inspects the response and can replace it  
  
  * An input guardrail blocks disallowed requests before they cost a model call

  * An output guardrail catches disallowed content before the user sees it

  * A guardrail that should apply everywhere belongs in a plugin

  * A guardrail specific to one agent belongs in that agent’s callback

#### 6.5.1. An Output Guardrail in Practice

An output guardrail returns a replacement `LlmResponse` to scrub disallowed content.
    
    
    def redact_secrets(callback_context, llm_response):
        """Replaces the answer if it leaks an API key."""
        text = llm_response.content.parts[0].text
        if "sk-" in text:
            return LlmResponse(
                content=types.Content(
                    role="model",
                    parts=[types.Part(text="[redacted: response withheld]")],
                )
            )
        return None  # let the response through

### 6.6. Automated Evaluation With Evaluation Sets

Manual spot-checking does not scale. ADK evaluates an agent automatically against saved cases.

#### 6.6.1. Test Files Versus Evaluation Sets

Artifact | What it holds  
---|---  
Evaluation case | One input and what a good run looks like: the expected tools and response  
Evaluation set | A collection of cases, saved as an `.evalset.json` file  
  
  * Capture a case by running the agent and saving its session as an eval case

  * Assemble several cases into one evaluation set

  * Re-run the set whenever the agent changes; it becomes a regression test for behavior

#### 6.6.2. The Evaluation Pipeline

#### 6.6.3. Trajectory and Response Criteria

An evaluation case is scored against **criteria**. Two cover most needs.

Criterion | What it measures  
---|---  
`tool_trajectory_avg_score` | Did the agent call the expected tools, with the expected arguments?  
`response_match_score` | How closely does the final answer match the reference answer?  
  
  * Each criterion has a threshold the agent must meet to pass

  * Criteria and thresholds live in a `test_config.json` file

  * Trajectory checks **how** the agent worked; response checks **what** it produced

#### 6.6.4. Criteria in test_config.json

      "criteria": {
        "tool_trajectory_avg_score": 1.0,

#### 6.6.5. Running an Evaluation

### 6.7. Hallucination and Drift Detection With LLM-as-Judge

A reference-match score is exact-minded: it cannot tell a correct paraphrase from a wrong answer. **LLM-as-judge** criteria use a model to judge meaning.

Criterion | What the judge model decides  
---|---  
`final_response_match_v2` | Does the answer mean the same as the reference, even if worded differently?  
`hallucinations_v1` | Is each sentence of the answer grounded in the available context?  
`rubric_based_*` | Does the answer satisfy a written rubric you supply?  
  
  * A judge criterion sets a `threshold` and `judge_model_options`

  * `final_response_match_v2` rescues correct answers that `response_match_score` marks down for wording

  * `hallucinations_v1` labels each sentence as `supported`, `unsupported`, `contradictory`, `disputed`, or `not_applicable`; the score is the fraction of sentences that are `supported` or `not_applicable`, exposing drift sentence by sentence

LLM-as-judge criteria cost an extra model call per case, so they are not free, but they measure things a string comparison cannot. The practical pattern is a layered one: keep the cheap, deterministic criteria (`tool_trajectory_avg_score`, `response_match_score`) as the fast first gate, and add judge criteria where wording varies or groundedness matters. Because a judge is itself a model, treat its verdicts as strong signal rather than absolute truth, and sample more than once where a case is borderline.

### 7.2. Why Orchestration

A single agent decides its own next step on every turn. That flexibility is useful, but when the steps are known in advance, it introduces unpredictability that makes the pipeline harder to test and to cost.

**LLM improvisation**

  * The model chooses the order of work

  * Flexible, but variable run to run

  * Hard to test and to cost

**Deterministic orchestration**

  * You fix the order of work

  * Same structure every run

  * Predictable, testable, traceable

  * **Orchestration** is fixing the control flow yourself instead of letting the model improvise it

  * When the steps are known, a deterministic workflow removes a whole class of failures

  * The model still does the **thinking** inside each step; orchestration only fixes the **sequence**

### 7.3. Sequential, Parallel, and Conditional Patterns

Three control-flow patterns cover most orchestration needs.

Pattern | Shape  
---|---  
Sequential | Step after step: each step’s output feeds the next  
Parallel | Several steps at once: independent work, run concurrently  
Conditional | A branch: the path taken depends on a decision  
Loop [1] | A step repeated until a condition is met  
  
[1] Loop is expressed via a dynamic workflow (a `@node` function with a `while` loop), not a single graph edge; see _Loop: Use a Dynamic Workflow_.

  * Sequential when each step depends on the one before

  * Parallel when steps are independent and you want them faster

  * Conditional when the work differs by input

  * Loop when a step refines its own result

#### 7.3.1. The Three Shapes at a Glance

### 7.4. The ADK 2.0 Workflow Graph

ADK 2.0 expresses all four patterns with one construct: the `Workflow` class, a **graph** of nodes connected by edges.

  * A `Workflow` holds a list of `edges`

  * A **node** is an agent, a tool, a `JoinNode`, or a plain function

  * Agents and functions are placed directly inside an edge tuple

  * The string `"START"` marks the graph’s entry point

  * The `Workflow` runs by following edges from `"START"`

#### 7.4.1. A Minimal Workflow Graph

Two agents, one edge: a `Workflow` that plans, then writes.
    
    
    from google.adk import Workflow
    
    workflow = Workflow(
        name="report_workflow",
        edges=[
            ("START", plan_agent, write_agent),
        ],
    )

#### 7.4.2. Sequential: a Chain in One Tuple

  * List all the sequential nodes in a single edge row: `("START", a, b, c)`

  * Each node’s output is passed as the next node’s input

  * Nodes can read and write shared state through `ctx.session.state` when they take a `Context` argument

#### 7.4.3. Parallel: Fan-Out and a JoinNode

  * Each parallel branch is its own edge row from the same source

  * A `JoinNode` waits for every branch to emit an `Event` before continuing

  * The join collects each branch’s output and passes it to the next node

#### 7.4.4. Parallel: Edge Example
    
    
    from google.adk import Workflow
    from google.adk.workflow import JoinNode
    
    my_join_node = JoinNode(name="my_join_node")
    
    workflow = Workflow(
        name="research_workflow",
        edges=[
            ("START", researcher_a, my_join_node),
            ("START", researcher_b, my_join_node),
            (my_join_node, writer),
        ],
    )

#### 7.4.5. Parallel: the Graph

Each branch runs independently, then `JoinNode` gates the next step until both complete.

#### 7.4.6. Conditional: a Routing Map

  * A **router** is a function that inspects its input and returns `Event(route="VALUE")`

  * The edge’s destination is a **routing map** (`{value: node}`)

  * The run follows the entry whose key matches the router’s `route`

    
    
    from google.adk import Event, Workflow
    
    def route_request(node_input: str):
        """Routes by request type."""
        text = node_input.lower()
        if "summary" in text:
            return Event(route="summary")
        return Event(route="report")

#### 7.4.7. Conditional: Workflow Edges
    
    
    from google.adk import Workflow
    
    workflow = Workflow(
        name="routing_workflow",
        edges=[
            ("START", classify_agent, route_request),
            (route_request,
                {
                    "summary": summary_node,
                    "report": report_node,
                },
            ),
        ],
    )

#### 7.4.8. Conditional: the Graph

The router sends the run down whichever edge matches the `route` value on its returned `Event`.

#### 7.4.9. Loop: Use a Dynamic Workflow

Graph routes flow forward. For iteration (refine until reviewed, retry until success), ADK 2.0 teaches a **dynamic workflow** : a `@node`-decorated `async` function that calls `ctx.run_node(…​)` in an ordinary Python `while` loop.

#### 7.4.10. Loop: Dynamic Node Example
    
    
    from google.adk import Context, Event
    from google.adk.workflow import node
    
    @node
    async def write_and_review(ctx: Context, brief: str):
        code = await ctx.run_node(writer_agent, brief)
        review = await ctx.run_node(reviewer_agent, code)
        while review.findings:
            yield Event(state={"code": code, "findings": review.findings})
            code = await ctx.run_node(
                writer_agent, {"code": code, "findings": review.findings})
            review = await ctx.run_node(reviewer_agent, code)
        return code

#### 7.4.11. Loop: Attach to the Graph
    
    
    from google.adk import Workflow
    
    workflow = Workflow(
        name="review_loop",
        edges=[("START", write_and_review)],
    )

  * The loop lives in ordinary Python: `while`, `async`, `await`

  * `ctx.run_node` runs another node and returns its output

  * Dynamic workflows checkpoint each `run_node` call, so a resumed run skips already-completed iterations

#### 7.4.12. Loop: the Graph

#### 7.4.13. The Four Shapes, Recapped

You have now expressed all four patterns in one graph model:

Shape | How it is expressed  
---|---  
Sequential | Nodes listed in one edge tuple  
Parallel | Multiple edges feeding a shared `JoinNode`  
Conditional | A router node returning `Event(route=…​)` into a routing map  
Loop | A `@node` dynamic workflow with a Python `while`  
  
### 7.5. Function Nodes: Running Code Without an LLM

Not every step needs a model. A **function node** wraps a plain Python function.

  * A plain function can be dropped directly into an `edges` row; ADK wraps it for you

  * For more control, use the `@node(name=…​)` decorator or instantiate `FunctionNode(…​)` explicitly

  * It runs ordinary code: no model call, no token cost

  * A function can take `ctx: Context` to read and write workflow state through `ctx.session.state`

  * Routers, validators, and formatters are natural function nodes

#### 7.5.1. Function Node Example: Decorator
    
    
    from google.adk import Context
    from google.adk.workflow import node
    
    @node(name="format_output")
    def format_output(node_input: str, ctx: Context):
        ctx.session.state["last_format"] = node_input  # write shared state
        return node_input.strip().upper()

#### 7.5.2. Function Node Example: Explicit FunctionNode
    
    
    from google.adk.workflow import FunctionNode
    
    format_node = FunctionNode(
        format_output,
        name="format_output",
        rerun_on_resume=True,
    )

A router that decides which branch to take is pure logic: it should not cost a model call, and it should behave identically every run. Making it a function node keeps the decision deterministic and free. The model is then spent only inside the nodes that genuinely need to reason, and the graph around them stays cheap and testable.

### 7.7. Error Propagation, Recovery, and Reflect-and-Retry

In a workflow, an unhandled error in one node stops the run. ADK gives two recovery tools.

#### 7.7.1. Recovery Mechanisms

Mechanism | What it does  
---|---  
Retry configuration | Re-runs a failed node automatically, with backoff, up to a limit  
Reflect-and-retry | Feeds the error back to the model so it can correct its next attempt  
  
  * A `RetryConfig` on a node sets `max_attempts` and the backoff between tries

  * Plain retry suits **transient** failures (a timeout, a brief outage)

  * Reflect-and-retry suits failures the model can **fix** (a bad argument, a malformed call)

#### 7.7.2. Retry Configuration Example
    
    
    from google.adk.workflow import FunctionNode, RetryConfig
    
    fetch_node = FunctionNode(
        fetch_sources,
        name="fetch",
        retry_config=RetryConfig(max_attempts=3),
    )

#### 7.7.3. Reflect-and-Retry Example

Plain retry repeats the same call; reflect-and-retry feeds the error back so the next attempt can change. A dynamic node expresses it (illustrative):
    
    
    @node(name="write_and_fix")
    async def write_and_fix(ctx: Context):
        error = None
        for _ in range(3):
            result = await ctx.run_node(writer, error_hint=error)
            ok, error = validate(result)
            if ok:
                return result
        return result  # best effort after retries

#### 7.7.4. Implementation Rule

Recall the ADK 2.0 rule: do not catch exceptions inside a tool; let them propagate so retry can fire.

### 7.8. Checkpointing, Session Resumption, and Rewind

A long workflow may be interrupted (a crash, a pause for human input). ADK can pick it back up.

Capability | What it gives you  
---|---  
Checkpointing | The run’s progress is recorded as it goes  
Session resumption | An interrupted run continues from where it stopped  
Rewind | A session is rolled back to an earlier point and re-run from there  
  
  * Resumption means a multi-step workflow does not restart from zero after an interruption

  * Rewind is for correction: go back before a bad step and take a different path

  * Both build on the event log: the session’s events are the record the run is rebuilt from

### 7.9. Choosing Deterministic Workflows Over LLM-Driven Coordination

Not every task should be a workflow. Use this as a decision guide.

Prefer a deterministic workflow | Prefer LLM-driven coordination  
---|---  
The steps are known in advance | The steps depend on what the user asks  
The order rarely changes | The order is genuinely open-ended  
You need predictable cost and tests | Flexibility matters more than predictability  
Failures must be handled the same way | The model can reasonably decide what to do  
  
The honest default is to reach for a deterministic workflow whenever the steps are known, and to fall back to LLM-driven coordination only where the work genuinely cannot be laid out in advance. A workflow you can read, test, and cost is worth more than flexibility you do not need. Many real systems are a mix: a deterministic graph for the known pipeline, with one LLM-coordinated step where the path is truly open.

### 8.2. The Escalation Ladder

ADK gives you four levels of capability. Climb a rung only when the problem demands it.

Rung | Construct | Use when  
---|---|---  
1 | Single agent with tools | One agent can do the job; tools extend its reach  
2 | Session state + callbacks | The agent needs memory across turns, guardrails, or lifecycle hooks  
3 | Workflow graph (sequential, parallel, loop, conditional) | Deterministic orchestration matters; LLM-driven control flow is not safe or predictable enough  
4 | Sub-agents / agent teams | The problem requires specialization, parallel independent branches, or independently deployed components  
  
The escalation rule: if Rung 1 fails, add to Rung 1 before moving to Rung 2. If Rung 2 fails, move to Rung 3. Never jump rungs because a higher rung sounds more powerful.

### 8.3. When to Add a Sub-Agent

A sub-agent is the right choice when one or more of these four conditions applies.

Condition | What it means in practice  
---|---  
Specialization | The sub-task needs a distinct instruction set, a different model, or a different tool set that would clutter the parent  
Parallelism | The sub-tasks are genuinely independent and can run concurrently, saving wall-clock time  
Isolation | The sub-task should not see the parent’s full context, history, or state  
Reuse | The same specialist agent is called from two or more different coordinators  
  
If none of the four conditions applies, add a tool instead of a sub-agent.

#### 8.3.1. Tool vs. Sub-Agent Decision

Add a tool when | Add a sub-agent when  
---|---  
The action is deterministic (call an API, query a database) | The action requires LLM reasoning of its own  
The result fits in a single dict return value | The result is itself a multi-step conversation or workflow  
The parent needs full control of when and how it runs | The sub-task benefits from a different instruction or model  
You want testability with a simple mock return value | You want to test the sub-agent independently with FakeLlm  
  
### 8.4. The Over-Orchestration Trap

ADK 2.x removed the forced two-agent split that ADK 1.x required in some patterns. A single agent can now do more, which makes it easier to over-engineer.

#### 8.4.1. Signs of Over-Orchestration

  * A coordinator that delegates to a single sub-agent (one-to-one is just indirection)

  * Sub-agents whose only job is to call one tool (wrap the tool instead)

  * A workflow with sequential steps that each take one deterministic action (use a pipeline of tools)

  * More agent hops than user turns

#### 8.4.2. The Cost of Extra Hops

Each extra sub-agent adds at least one model call round trip, even if the sub-agent does nothing remarkable. That round trip means more billed tokens and added latency.

Pattern | Token impact  
---|---  
Coordinator delegates to sub-agent | +1 model call: coordinator decides, sub-agent executes, result returns  
Sub-agent wraps one tool call | Same total work as the coordinator calling the tool directly, plus one extra model step  
Three-level coordinator → specialist → tool | Every user turn costs three model calls minimum  
  
Keep the architecture as flat as the problem allows.

### 8.5. Evaluating Your Architecture

Before finalizing an architecture, run it through four questions.

#### 8.5.1. Testability

  * Can each agent be tested in isolation with `FakeLlm`?

  * Can you assert on tool trajectory (which tools are called, in what order, with what arguments)?

  * Can you force an error path without calling the real model?

An architecture that cannot be tested in isolation is an architecture that accumulates bugs silently.

#### 8.5.2. Token Cost

  * How many model calls does a single user turn require at minimum?

  * Which calls add the most tokens to the context window?

  * Would merging two sub-agents into one reduce calls without losing anything?

#### 8.5.3. Latency

  * Are parallel sub-agents justified by the latency savings?

  * If parallel branches take 2 s each and the sequential alternative takes 4 s, is 2 s worth the complexity?

  * Does the user actually wait for the result, or is it an async background job?

#### 8.5.4. Observability

  * Does the Dev UI Traces tab show you where time and tokens are spent?

  * Are sub-agent spans nested so you can read the tree top-down?

  * Can you reproduce a bad run deterministically (same input, same `FakeLlm` script)?

### 8.6. ADK Evaluation Tooling

ADK ships the tools you need to evaluate agent behavior. These are distinct from cost monitoring; they test correctness.

#### 8.6.1. `adk eval` and Evalsets

  * An evalset is a JSON file of input/expected-output pairs

  * `adk eval --eval_set_file my_evals.json` runs the set and reports pass/fail

  * Evalsets belong in version control alongside agent code

#### 8.6.2. test_config.json Criteria

Criterion | What it checks  
---|---  
`response_match` | The final response contains or matches expected text  
`tool_trajectory` | The agent called specific tools, in a specific order, with specific arguments  
`output_schema` | The response validates against a Pydantic model (when `output_schema` is set)  
  
#### 8.6.3. LLM-as-Judge: When and What It Costs

  * Use LLM-as-judge for criteria that cannot be expressed as exact matches

  * Each judgment call is itself a model call — budget accordingly

  * Reserve LLM-as-judge for subjective quality checks; use trajectory and schema checks for correctness

#### 8.6.4. FakeLlm: Unit Testing Without Model Calls

### 9.2. Single Agent Versus Multiple Agents

One capable agent can do a lot. Splitting a problem across several agents is a deliberate choice, so make it for a reason.

Reason to split | What it buys you  
---|---  
Specialization | Each agent has a focused instruction and a small tool set  
Parallelism | Independent sub-tasks can run at the same time  
Maintainability | A small, single-purpose agent is easier to test and change  
  
  * A single agent is simpler; prefer it until a reason to split appears

  * An over-stuffed agent with many tools and a sprawling instruction is the signal to split

  * Splitting adds coordination cost; the specialization has to be worth it

### 9.3. Hierarchical Agent Teams

The common multi-agent shape is a hierarchy: one **coordinator** over several **sub-agents**.

  * A coordinator is an `LlmAgent` with a `sub_agents` list

  * Each sub-agent is a specialist: billing, technical support, or scheduling

  * The coordinator reads the request and hands it to the right sub-agent

  * When a sub-agent finishes, control returns to the coordinator

#### 9.3.1. Defining a Coordinator

A coordinator is an `LlmAgent` whose `sub_agents` list names its specialists.
    
    
    model = "gemini-flash-latest"
    
    coordinator = LlmAgent(
        name="support_coordinator",
        model=model,
        instruction="Route billing questions to billing_agent and "
                    "technical questions to tech_agent.",
        sub_agents=[billing_agent, tech_agent],
    )

#### 9.3.2. Returning Control to the Parent

  * A sub-agent handles its piece, then hands control back up

  * The coordinator can then respond, or delegate again

  * This return of control is what makes it a **team** , not a one-way handoff

### 9.4. Agent Transfer Versus Agent-as-Tool

There are two ways a coordinator can use another agent. They differ in **who decides**.

| Agent transfer | Agent-as-tool  
---|---|---  
How | Listed in `sub_agents` | Wrapped in `AgentTool`, listed in `tools`  
Who decides | The model decides to transfer | The model calls it like any tool  
Control | Flexible, LLM-driven | Explicit and deterministic  
Result | The sub-agent may take over the turn | The result returns to the caller, like a tool result  
  
#### 9.4.1. Agent-as-Tool in Code

Wrap a specialist in `AgentTool` and list it in `tools`.
    
    
    from google.adk.tools.agent_tool import AgentTool
    
    model = "gemini-flash-latest"
    
    coordinator = LlmAgent(
        name="coordinator",
        model=model,
        instruction="Use the billing tool for billing questions.",
        tools=[AgentTool(agent=billing_agent)],
    )

Use **transfer** (`sub_agents`) when you want the specialist to genuinely take over the conversation, the way a help desk routes a caller to a department. Use **agent-as-tool** (`AgentTool`) when you want a contained answer back: the coordinator stays in charge, calls the specialist like a function, and folds the result into its own reply. Transfer is flexible and LLM-driven; agent-as-tool is explicit and predictable. When you need the coordinator to remain the single voice to the user, agent-as-tool is the safer choice.

### 9.5. Shared Versus Isolated Context

Agents in a hierarchy do not all see the same thing.

Context | Who shares it  
---|---  
Session state | Shared down the hierarchy through the invocation context  
Parallel branches | Isolated from each other while they run  
Task branches | Isolated: a contained unit of work  
  
  * A sub-agent reached by transfer shares the session’s state with its coordinator

  * Parallel branches are deliberately isolated so they cannot interfere

  * Use `output_key` to publish a branch’s result back to shared state

  * The narrowest context that still does the job is the right one

  * Register a plugin once on the `App` handed to the `Runner`; it covers the whole hierarchy

One registration enforces a single policy across every agent in the team.

### 9.7. Structuring a Multi-Agent Project

File layout follows the communication structure. Keep each agent as a Python package so imports are clear and tests can target each agent independently.

#### 9.7.1. Coordinator-and-Sub-Agents Layout
    
    
    my-team/                    ← project root
        coordinator/            ← coordinator package
            __init__.py
            agent.py            ← root_agent (the coordinator)
            tools.py
        researcher/             ← sub-agent package
            __init__.py
            agent.py            ← the researcher sub-agent
            tools.py
        writer/                 ← sub-agent package
            __init__.py
            agent.py            ← the writer sub-agent
            tools.py
        shared/
            prompts.py          ← shared prompt strings
        pyproject.toml

  * The coordinator’s `agent.py` imports sub-agents and registers them in `sub_agents`

  * Each sub-agent package is testable in isolation with `FakeLlm`

  * `shared/` holds content that multiple agents need; keep it small

#### 9.7.2. Flat vs. Package Layout

For simple teams with two or three agents, a flat layout in one module is fine:
    
    
    my-team/
        agent.py         ← defines coordinator, billing_agent, tech_agent
        tools.py
        pyproject.toml

Split into packages when an individual sub-agent grows its own tools, its own tests, or when it is reused from multiple coordinators.

#### 9.7.3. A2A Layout: Two Separate Projects

A2A agents run as independent services. Each one is its own project with its own `pyproject.toml` and venv.
    
    
    tech-service/               ← the remote agent project
        tech_agent/
            agent.py
            tools.py
        pyproject.toml
        .env
    
    client-coordinator/         ← the coordinator project (calls tech-service over A2A)
        coordinator/
            agent.py            ← uses RemoteA2aAgent pointing at tech-service
        pyproject.toml
        .env

  * Each project is started and stopped independently

  * API keys and config live in each project’s `.env`

  * The coordinator never imports the remote agent’s code; it only knows the agent card URL

### 9.8. Remote Agents and the A2A Protocol

So far every agent has run in the same process. **A2A** (the Agent2Agent protocol) lets an agent run as a separate networked service.

__Note

ADK’s A2A integration is **experimental** as of ADK 2.x. The A2A protocol specification is GA under the Linux Foundation, but the ADK library API may change, so expect an experimental-feature warning at run time and check the ADK release notes before relying on it in production.

| Local sub-agent | Remote A2A agent  
---|---|---  
Where it runs | The same process | Its own service, over the network  
Coupling | Shipped and deployed together | Deployed and scaled independently  
Use when | The team is one application | Teams are owned separately or scaled separately  
  
#### 9.8.1. Exposing an Agent as an A2A Server

  * `to_a2a(agent, port=…​)` turns an agent into a web service

  * It publishes an **agent card** : a description of what the agent does

  * The card is served at `/.well-known/agent-card.json`

    
    
    from google.adk.a2a.utils.agent_to_a2a import to_a2a
    
    a2a_app = to_a2a(tech_agent, port=8001)
    # run with:  uvicorn a2a_server:a2a_app --host localhost --port 8001

#### 9.8.2. Consuming a Remote Agent

  * `RemoteA2aAgent` is a local stand-in for a remote agent

  * Give it the URL of the remote agent’s card

  * It behaves like any other agent; drop it into `sub_agents`

    
    
    from google.adk.agents.remote_a2a_agent import RemoteA2aAgent
    
    tech_agent = RemoteA2aAgent(
        name="tech_agent",
        description="Remote technical-support specialist.",
        agent_card="http://localhost:8001/.well-known/agent-card.json",
    )

The proxy satisfies the same agent interface, so the coordinator code does not change.

### 10.2. Why Testing Agents Is Hard

A normal unit test asserts that the same input gives the same output. An agent breaks that assumption.

Problem | Why it breaks a test  
---|---  
Non-determinism | The model can word the same answer differently every run  
External dependencies | A tool may call a live API that is slow, paid, or down  
Stochastic output | Two runs can even take different tool paths  
  
  * You cannot assert on exact model wording; it changes

  * You cannot depend on a live API in a fast, repeatable test

  * The fix: remove the non-determinism from the test, not from the agent

### 10.3. Unit-Testing With Mocked Model Backends

The key move is to replace the real model with a **mock** : a scripted stand-in that returns exactly what the test needs.

  * A mock model is supplied to the agent in place of a Gemini identifier

  * It returns canned responses: a fixed tool call and a fixed final answer

  * With the model fixed, the test is deterministic and offline

  * Now the test exercises your tools and wiring, nothing else

#### 10.3.1. What to Assert

Assertion | What it verifies  
---|---  
Tool trajectory | The agent called the expected tools, in the expected order  
Final output | The agent produced the expected structured result  
Error path | A failing tool degrades gracefully instead of crashing  
      
    
    async def test_agent_calls_weather_tool():
        agent = build_weather_agent(model=FakeLlm(...))
        events = await run_agent(agent, "What's the weather in Paris?")
        tool_calls = [c.name for e in events for c in e.get_function_calls()]
        assert "get_weather" in tool_calls

#### 10.3.2. The Agent Evaluator in a Test

  * `AgentEvaluator.evaluate(…​)` can run inside a `pytest` test

  * It checks an agent against a saved evaluation set

  * Point it at a mock-backed build of the agent to keep the test deterministic

  * This puts trajectory and response evaluation into the test suite

Two layers of testing work together. Mocked-model unit tests are fast and deterministic: they prove your tools and wiring behave. Evaluation tests, run through `AgentEvaluator`, check the agent against saved cases and criteria. Run the evaluator against a mock-backed agent and the whole suite stays deterministic and offline; run it against the real model and it becomes an integration check you run less often. Test at least one error path in every suite. A tool returning a `status: "error"` dict should never crash the run.

### 10.4. Observability Through OpenTelemetry

A test proves the agent works before release. **Observability** shows what it does in production.

  * ADK instruments runs with **OpenTelemetry** , an open tracing standard

  * A **span** records one unit of work, with timing and detail

  * Spans nest: an agent-run span contains tool-call and model-call spans

  * Spans are exported in the **OTLP** format to a backend such as Cloud Trace

  * Enable Cloud Trace export with the `--otel_to_cloud` flag on `adk web`/`adk api_server` (or set the standard OTLP environment variables)

#### 10.4.1. The Three Span Types

Span | What it records  
---|---  
Agent run | The whole invocation, end to end  
Model call | One request to the model, with token counts  
Tool call | One tool invocation, with arguments and result  
  
  * A trace answers "what did this request actually do, and where did the time go?"

  * Any OTLP-compatible backend stores and visualizes the exported spans

#### 10.4.3. Reading a Trace

### 10.5. Serving Agents as FastAPI Endpoints

### 10.7. Usage Tracking and Cost-Quality Trade-offs

A deployed agent costs money on every call. Production work means watching that.

  * Every model call reports **token usage** : input and output tokens

  * Tokens are the unit of cost; usage tracking turns runs into a cost figure

  * A larger model usually answers better and costs more per call

  * The trade-off: pick the smallest model that meets your quality bar

Token counts ride on the model-response event’s `usage_metadata`.
    
    
    async for event in runner.run_async(...):
        if event.usage_metadata:
            print(event.usage_metadata.prompt_token_count,
                  event.usage_metadata.candidates_token_count)

Model selection is an engineering decision, not a default. A bigger model is not automatically the right one; it costs more on every single call, and for many tasks a smaller, cheaper model clears the quality bar set by your evaluation suite. The disciplined approach ties the two halves of this module together: use the evaluation suite to measure quality, use usage tracking to measure cost, and choose the model that satisfies the quality criteria at the lowest cost.

### 11.7. Key Takeaways

  * An agent is an **LLM plus surrounding machinery** : tools, sessions, memory, and a runtime loop. ADK supplies the machinery; the model supplies the reasoning.
