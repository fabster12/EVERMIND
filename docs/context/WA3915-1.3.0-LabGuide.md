# Accelerated Building AI Agents with Google ADK

## Building a First ADK Agent Across Multiple Model Backends

Lab 1

  * Create and run a basic ADK agent using the adk command-line interface
  * Implement a function tool and register it with an agent
  * Inspect an agent’s events and traces in the ADK Dev UI
  * Configure the agent’s model backend through an environment variable
  * Run an agent asynchronously with a Runner and read the events it produces

### 1.1. Introduction

The Agent Development Kit (ADK) turns a large language model into an agent: a model paired with instructions, tools, and a runtime that decides when the task is done. In this lab you build that first agent.

You will complete a small **city assistant** , an agent that answers questions about the current time in a city by calling a tool. Along the way you will run the agent two ways, explore it in the ADK Dev UI, and see how a single setting swaps the model the agent runs on.

### 1.2. Framework and Tools

**Google ADK**

  * The `LlmAgent` class: defines a model-driven agent

  * Function tools: plain Python functions an agent can call

  * The `adk` command-line interface: `adk run` and `adk web`

  * The ADK Dev UI: a browser view of events, traces, and state

**Astral UV**

  * Each lab is a `uv` project; `uv sync` provisions its environment

  * `uv run` executes commands inside that environment

### 1.3. The Scenario

You are building a travel-support assistant for a company with offices around the world. The first capability the team needs is simple: an employee should be able to ask what time it is in any office city and get a clear answer.

A plain model call cannot answer this reliably; it has no clock. An agent can: it calls a tool that returns the time, then phrases the answer naturally. This lab builds that agent.

## Building an ADK Document Classifier with Validated Structured Output

Lab 2

  * Define a Pydantic output schema for an agent’s result
  * Constrain an agent’s response with an output schema
  * Enforce business rules on the result with a field validator
  * Capture a validated result in session state with a named result key
  * Retry low-confidence classifications and fall back to a safe default

### 2.1. Introduction

An agent that returns a typed, validated object gives code something to build on; prose responses change shape with every call. In this lab you build a document classifier whose every response has the same fields, the same types, and passes the same business rules.

You will define a Pydantic schema, attach it to an agent, add a validator that rejects invalid categories, capture each result in session state, and add a retry-and-fallback strategy for low-confidence results. The optional challenge adds a router that sends documents to specialized extraction agents.

### 2.2. Framework and Tools

**Google ADK**

  * `output_schema`: constrains an agent’s response to a schema

  * `output_key`: writes the result into session state

**Pydantic**

  * `BaseModel`: defines a schema as a typed class

  * `Field`: adds constraints such as numeric ranges

  * `field_validator`: enforces business rules beyond types

### 2.3. The Scenario

An operations team receives a steady stream of documents (invoices, support tickets, product reviews, and meeting notes) into one shared inbox. They want each document tagged automatically so it can be routed to the right queue.

A plain model call would describe each document differently every time. The team needs a **classifier** whose output is predictable enough to drive automation: a category from a fixed list, a confidence score, and a short summary.

### 2.8. Core Lab Part 2: Retry Low-Confidence Results

A classifier is not always sure. When confidence is low, one good strategy is to try again, and to fall back to a safe default if repeated attempts still fall short. Production classifiers need this resilience; a low-confidence guess silently treated as fact is worse than an honest `"unknown"`.

  1. Open `classify_with_retry.py`. The runner setup and a `run_once()` helper are provided, along with `CONFIDENCE_THRESHOLD` and `MAX_ATTEMPTS` constants.

  2. Replace the `YOUR CODE HERE - Step 4` placeholder in `classify_with_retry()` so it:

     * Runs the classifier up to `MAX_ATTEMPTS` times using the provided `run_once()` helper

     * Returns the first result whose `confidence` is at least `CONFIDENCE_THRESHOLD`

     * If no attempt clears the threshold, returns a fallback dict with category `"unknown"`, confidence `0.0`, and a summary explaining that classification was not confident

Your completed code should follow this shape:
    
    for attempt in range(1, MAX_ATTEMPTS + 1):
        result = await run_once(runner, text, attempt)
        if result.get("confidence", 0.0) >= ...:
            return result
    return {"category": "unknown", "confidence": ..., "summary": "..."}

  3. Run it:
         
         uv run classify_with_retry.py

### 7.1. Introduction

A support desk does not ask one person to handle billing, networking, and account questions. It routes each caller to a specialist. In this lab you build that pattern as an agent team (a coordinator over two specialists) and then take one specialist out of the process entirely, running it as a networked A2A service the coordinator reaches over the wire.

__Note

ADK’s A2A integration is **experimental** as of ADK 2.x. The A2A protocol specification is GA under the Linux Foundation, but the ADK library API may change; expect an experimental-feature warning at run time, and check the ADK release notes before relying on it in production.

**Astral UV and Uvicorn**

The lab is a UV project; the A2A server runs under Uvicorn.

### 7.3. The Scenario

**Validation:** The script runs the suite and exits with status `0` when every test passes, which is exactly what a CI pipeline checks.

**Reference solutions:** `solutions/run_tests.ps1` and `solutions/run_tests.sh`.

### 8.9. Working with pytest

pytest discovers and runs any function named `test_*` in files named `test_*.py`. A few flags make it easier to work with while you develop; all run through `uv run` so they use the lab’s environment:

Command | What it does  
---|---  
`uv run pytest -q` | Quiet: one line of dots plus the summary (what the lab uses)  
`uv run pytest -v` | Verbose: lists each test name with `PASSED` / `FAILED` / `SKIPPED`  
`uv run pytest -k weather` | Run only tests whose name contains `weather`; handy for one test at a time  
`uv run pytest -x` | Stop at the first failure instead of running the whole suite  
`uv run pytest --no-header -rA` | Show a short reason for every result, including why a test was skipped  
  
Read the last line first: `4 passed in 2.5s`, or `3 passed, 1 failed`; the counts tell you the state at a glance, and a failure prints the failing assertion with the expected and actual values right above the summary. This lab sets `asyncio_mode = "auto"` in `pyproject.toml` so `async def` tests run without extra decorators; that is why the suite must run through `uv run` (which loads the project config) rather than a globally installed `pytest`.

## Deploying an ADK Agent to Agent Runtime with Tracing

Lab 9

  * Serve an agent as a FastAPI endpoint with the adk CLI
  * Export OpenTelemetry traces to Cloud Trace
  * Deploy the agent to Agent Runtime
  * Analyze trace spans and usage data

### 9.1. Introduction

A working agent needs an HTTP interface, tracing, and a managed deployment target before it can run in production. In this lab you add all three: serve the agent as a web API, export traces so you can see what each request does, and deploy it to a managed cloud runtime.

### 9.2. Framework and Tools

**Google ADK**

  * `adk api_server`: serves an agent as a FastAPI application

  * The `/run` and `/run_sse` endpoints: complete and streamed responses

  * `--otel_to_cloud`: exports OpenTelemetry traces to Cloud Trace

  * `adk deploy agent_engine`: deploys an agent to Agent Runtime

**Google Cloud**

The tracing and deployment steps need a Google Cloud project with billing enabled and the `gcloud` CLI.

### 9.3. The Scenario

A store FAQ assistant is finished and tested. The team now needs it running as a service, with observability so they can see how requests behave, and deployed to a managed runtime rather than a developer’s machine.

### 9.4. Project Structure
    
    
    deploying-an-adk-agent-to-agent-runtime/
    ├── assistant/
    │   ├── __init__.py
    │   └── agent.py               # the agent to serve and deploy (provided)
    ├── call_endpoints.py          # Core Lab – call the served endpoints
    ├── solutions/
    │   └── call_endpoints.py      # completed Core Lab script, for reference
    ├── pyproject.toml             # UV project and dependencies
    └── .env.example                # copy to .env and add your API key

Before you begin, know the role of each file:

  * **Files you edit:** `call_endpoints.py` (Core Lab)

  * **Files you run but do not edit:** `assistant/agent.py`, the agent you serve and deploy

  * **Reference only:** everything in `solutions/`; check your work against these, or use them to catch up

  * **Do not modify:** `assistant/_init_.py`, `pyproject.toml`

### 9.5. Problem Statement

**Time Allocation:** 70-85 minutes

**Objective:** Serve the FAQ assistant locally through the adk API server, enable trace export, and deploy it to Agent Runtime.

**Expected Outcome:** A `call_endpoints.py` that exercises the local `/run` endpoint (and, in non-Vocareum environments, `/run_sse`), and (for students with a Google Cloud project) the agent deployed to Agent Runtime and answering a request.

__Note

Steps 2 through 4 and both challenges need a Google Cloud project with billing enabled. If you do not have one, Step 1 runs fully on your machine, and the **Without a Google Cloud Project** section below gives a local path for the rest, including reading trace spans in the Dev UI instead of Cloud Trace. See the course setup guide for how to obtain a Gemini API key and (optionally) a Cloud project.

### 9.6. Getting Started

  1. Open a terminal and change into the lab directory:
         
         cd LabFiles/deploying-an-adk-agent-to-agent-runtime

  2. Install dependencies:
         
         uv sync

  3. Copy the example environment file and fill in your credentials:
         
         cp .env.example .env

Open `.env` and set the values shown below. Your Gemini API key comes from the lab portal on the Vocareum page for this lab.
         
         GOOGLE_GENAI_USE_VERTEXAI=FALSE
         GOOGLE_GENAI_USE_ENTERPRISE=FALSE
         GEMINI_API_KEY=voc-<paste-your-key-here>
         GOOGLE_GEMINI_BASE_URL=https://gemini.vocareum.com
         ADK_MODEL=gemini-3.5-flash

All five variables are required. `GOOGLE_GEMINI_BASE_URL` points the SDK at the Vocareum Gemini proxy; without it your lab key will be rejected.

### 9.7. Core Lab: Serve, Trace, and Deploy

#### 9.7.1. Serve the Agent Locally

  1. In one terminal, start the API server:
         
         uv run adk api_server

**Expected output:**
         
         INFO:     Started server process [12345]
         INFO:     Uvicorn running on http://127.0.0.1:8000 (Press CTRL+C to quit)

  2. In a second terminal, open `call_endpoints.py` and complete `call_run` at `# YOUR CODE HERE - Step 1` so it `POST`s to `{BASE_URL}/run` with a JSON body of `app_name`, `user_id`, `session_id`, and a `new_message`, then raises for errors and prints the response.

Your completed code should follow this shape:
         
         body = {
             "app_name": APP_NAME,
             "user_id": ...,
             "session_id": ...,
             "new_message": {"role": "user", "parts": [{"text": question}]},
         }
         response = httpx.post(f"{BASE_URL}/run", json=body)
         # raise for errors, then print the response JSON

  3. Run it:
         
         uv run call_endpoints.py

**Expected output** (abridged; your wording will vary, the model phrases each reply):
         
         Session created: demo-session
         
         --- /run (complete response) ---
         [{'content': {'parts': [{'functionCall': {'name': 'get_faq_answer', 'args': {'topic': 'hours'}}}], ...}, {'content': {'parts': [{'text': 'We are open 9am to 5pm, Monday through Friday.'}], ...}]
         
         --- /run_sse (streamed response) ---

Symptom | Likely cause and fix  
---|---  
Opening `<http://127.0.0.1:8000/>` in a browser shows `{"detail":"Not Found"}` | That is expected: `adk api_server` serves an API, not a web page, so the root path has no route. The server is fine. Confirm it is up by visiting `<http://127.0.0.1:8000/list-apps>` (returns `["assistant"]`) or `<http://127.0.0.1:8000/docs>` (the API explorer), or just run `call_endpoints.py`. `adk api_server` fails with `address already in use` | A previous server is still running on port 8000. Stop it with Ctrl-C in its terminal, or start this one on another port (and update `BASE_URL` in `call_endpoints.py` to match).

Requests succeed but no traces appear in Cloud Trace | The console is showing a different project, the Cloud Trace API is not enabled, or the traces have not arrived yet; exported spans can take a minute or two to appear.  
`adk deploy agent_engine` fails with a permissions, billing, or quota error | The `gcloud` account or project is not set up for deployment. Confirm `gcloud auth login` succeeded, the project has billing enabled, the Vertex AI API is enabled, and `--project` names the right project.
