### 2.2. What Are AI Coding Assistants?

LLM-powered tools embedded in your editor that understand code structure, not just syntax:

  * **Reasoning engines** : they analyze intent, not just patterns

  * **Context-aware** : they read your open files, imports, and project structure

  * **Multi-modal** : generation, refactoring, debugging, documentation, and review in one tool

  * **Iterative** : they improve output through conversation, not just single-shot completion

AI coding assistants are tools that:

  * Generate code

  * Explain or improve existing code

  * Help with debugging

  * Produce documentation

  * Build small multi-file structures

    * They rely on a Large Language Model (LLM) to understand your instructions and generate responses. The quality of their output depends entirely on the instructions you provide; vague prompts produce vague code.

#### 2.2.1. Architecture & Components

Component | Role  
---|---  
LLM | The reasoning and generation engine; processes tokens, produces output  
Context Manager | Determines what information the model sees for each request  
Tooling Layer | File access, terminal commands, Git operations  
Safety & Guardrails | Prevent harmful or unsafe actions  
IDE Integration | The interface developers interact with (extension, CLI, or standalone IDE)  
  
Every assistant packages these five components differently; the next slide compares how.

  * Extensions (Amazon Q, Copilot) add capabilities to your existing editor

  * CLI tools (Claude Code) operate directly in the terminal

  * Standalone IDEs (Cursor) replace the editor entirely

The integration model determines what the assistant can see and do.

AI coding assistants share the same core architecture (an LLM, a context manager, a tools layer, a safety system, and an integration surface) but they package it differently. The next slide covers how each tool packages these components.

#### 2.2.2. Integration Models

Each tool packages the same core components differently:

Agent | Integration Model  
---|---  
Amazon Q | IDE extension (VS Code, JetBrains) with chat panel and inline suggestions  
Copilot | IDE extension (VS Code, JetBrains, Neovim) with chat and completions  
Claude Code | Standalone CLI that operates directly in the terminal  
Cursor | Standalone IDE (VS Code fork) with assistant built into the editor  
  
The integration model determines what the assistant can see and do; a CLI tool has full filesystem access by default, while an IDE extension operates within the editor’s sandbox.

Amazon Q and Copilot install as extensions into your existing IDE. You keep your editor and add assistant capabilities. Claude Code takes a different approach: it runs as a CLI tool in your terminal, reading and writing files directly. Cursor replaces the IDE entirely; it ships as a modified VS Code with the assistant wired into every surface.

The integration model matters because it determines what the assistant can see and do. A CLI tool has full filesystem and terminal access by default. An IDE extension operates within the editor’s sandbox and needs explicit permissions for terminal or Git operations.

#### 2.2.3. Autonomy Levels

Assistants vary in how much they can do on their own:

  * **Level 0: Passive** : Autocomplete, inline suggestions

  * **Level 1: Reactive** : Responds to prompts, no independent action

  * **Level 2: Guided Autonomy** : Executes steps when instructed (run tests, modify files)

  * **Level 3: Semi-Autonomous** : Plans and executes multi-step tasks with oversight

  * **Level 4: Fully Autonomous** (emerging): End-to-end feature delivery with human approval

**Where each tool operates today:**

Agent | Description  
---|---  
Amazon Q | Level 0–2 (inline + chat), Level 3 with `/dev` agent  
Copilot | Level 0–2 (inline + chat), Level 3 in agent mode  
Claude Code | Level 2–3 by default, Level 3 with extended thinking  
Cursor | Level 0–2 (inline + chat), Level 3 in composer/agent mode  
  
Most assistants today operate across several levels depending on the mode you choose. Inline completions are Level 0. Chat is Level 1. When you give the assistant permission to run commands or edit files, you move to Level 2. Agent modes (Amazon Q `/dev`, Copilot agent mode, Claude Code’s default behavior, Cursor composer) operate at Level 3.

Level 4 is emerging but not yet standard. Some tools can plan and execute multi-step tasks end to end, but they still require human approval at key checkpoints. The autonomy level you choose should match the risk: autocomplete for small edits, agent mode for larger refactors with review at each step.

### 2.3. How Assistants Process Input

**The Input Pipeline:**

  * User prompt

  * Context assembly (files, codebase, history)

  * Tokenization

  * Model inference

  * Output tokens generated

  * Assistant actions (optional: file edits, commands)

Assistants do not "think." They process text in steps:

  1. You provide a prompt

  2. Context is gathered (files, history, system rules)

  3. Everything is broken into tokens

  4. The model predicts the best output one token at a time

Every step in this pipeline is mechanical. There is no "understanding"; just pattern matching over tokens. The better your input, the better the patterns the model can match against.

#### 2.3.1. Context Windows

The assistant can only "see" what fits in its context window

  * A context window is the maximum amount of text the model can process at once

  * Includes your prompt, file contents, conversation history, and system instructions

  * A 128K token window holds roughly **400 pages of text** : about **50 source files of 200 lines each**

  * A 10-turn conversation with file references can consume 30-40% of that budget before you ask your question

Bigger window ≠ better reasoning; but it determines how much of your codebase the assistant can work with at once.

A context window is the assistant’s working memory. Only text inside the window can be used to answer your prompt.

To put the numbers in perspective: a 128K token context window holds roughly 400 pages of text or about 50 source files of 200 lines each. That sounds large, but your prompt, conversation history, and system instructions all share the same budget. A long conversation with several file references can use half the window before you even ask your next question.

This is why focused, specific prompts outperform long rambling conversations. Every token you waste on vague context is a token the assistant cannot spend on your actual codebase.

#### 2.3.2. Token Limits

Tokens are the atomic units of text the model processes

  * 1 token ≈ 3-4 characters

  * Models have strict token limits

  * If you exceed the limit:

    * The assistant truncates

    * Or compresses context

    * Or refuses the request

Models have limits on how much text they can process.

If the limit is reached, the assistant may:

  * Drop old information

  * Summarize content

  * Refuse the task

    * When you hit the limit, the assistant is flying blind on whatever it dropped. Keep prompts focused and reference only the files that matter for the current task.

#### 2.3.3. Truncation & Compression

When context is too large, assistants must decide what to keep

**Truncation** :

  * Drops oldest or least relevant content

  * Risk: missing important details

**Compression** :

  * Summarizes content to fit

  * Risk: losing nuance

**Your job** :

Provide explicit references to the files or details that matter.

If your project is large, the assistant may remove or compress earlier content.

This can cause:

  * Missing details

  * Incorrect assumptions

  * Hallucinations

    * If you are several turns into a conversation and the assistant starts making mistakes it did not make earlier, context compression is likely the cause. Start a fresh conversation and re-attach the relevant files.

### 2.4. The Plan → Execute → Iterate Cycle

  * The most reliable workflow for multi-step tasks:

    * **Plan** : Ask the assistant to outline steps before writing code

    * **Execute** : Have it perform one step at a time

    * **Iterate** : Review output, refine the prompt, repeat

  * Prevents runaway actions and keeps the developer in control

The most reliable way to work with assistants:

  1. Plan; get the assistant to outline the steps

  2. Execute; tell it to perform one step only

  3. Iterate; review, refine, and move to the next step

Working this way keeps you in control. You catch mistakes at each step instead of discovering them after the assistant has rewritten half the file.

#### 2.4.1. Plan → Execute → Iterate in Practice

**Step 1; Plan (the initial prompt):**
    
    
    I need to add input validation to the checkout
    function in src/cart/checkout.ts. Before writing
    any code, outline what validations are needed
    and where each check should go.

**Step 2; Execute (one task at a time):**
    
    
    Implement the null cart check from step 1.
    Use an early return that throws InvalidCartError.
    Don't change anything else yet.

**Step 3; Iterate (refine based on output):**
    
    
    The null check works, but it doesn't handle
    an empty items array. Add that case to the
    same guard clause. Keep the error type consistent.

**What each step accomplishes:**

  * **Plan** : forces the assistant to reason before coding. You review the plan, not the code.

  * **Execute** : limits blast radius. One change, one review.

  * **Iterate** : you refine based on real output, not guesses. Each prompt builds on the last.

The developer stays in control at every stage.

Notice the pattern: the plan prompt says "before writing any code." This is deliberate. If you jump straight to "add validation," the assistant will write code immediately; and you lose the chance to shape the approach.

The execute prompt names the specific check, the specific error type, and explicitly says "don’t change anything else." Without that constraint, the assistant may "helpfully" refactor nearby code.

The iterate prompt references the previous output. This is how you build on results instead of re-prompting from scratch.

#### 2.4.2. Why Explicit Planning?

LLMs are powerful but not omniscient

  * They don’t know your intent unless you state it

  * They can hallucinate missing steps

  * They may take shortcuts

  * They benefit from structured constraints

Planning makes the workflow predictable and safe. Every major tool surfaces its plan before executing; learn what your tool does by default, and prompt for a plan explicitly when it does not offer one automatically.

Planning prevents the assistant from making assumptions, introducing unwanted changes, or skipping steps.

**How each tool surfaces its plan:**

Agent | Description  
---|---  
Amazon Q | `/dev` agent shows a step-by-step plan you approve before execution  
Copilot | Agent mode lists proposed actions; you accept or reject each one  
Claude Code | Prints its plan to the terminal and waits for confirmation before file edits  
Cursor | Composer shows a plan with diffs; you review before applying  
  
Every major tool now has a mechanism for showing you the plan before executing. The key difference is how much control you get: some tools show a high-level summary and let you approve the whole thing, while others show file-level diffs and let you accept or reject each change individually. Learn what your tool does by default, and prompt for a plan explicitly when it does not offer one automatically.

#### 2.4.3. Breaking Tasks Into Steps

**Instead of:**
    
    
    Build a login system.

**Break into steps:**

  1. Define requirements and constraints

  2. Generate folder structure

  3. Implement authentication logic

  4. Add tests for each module

  5. Integrate with existing code

__Tip

If reviewing a single step takes more than a minute, the step was too big.

Break work into small, clear actions. This helps the assistant produce clean, reliable results.

Good step breakdowns include:

  * Clear boundaries

  * Single responsibility actions

  * Observable outputs

  * Opportunities for review

Each step should be small enough that you can read the output in under a minute. If reviewing a single step takes longer than that, it was too big.

#### 2.5.1. File Operations

  * **How assistants interact with files:**

    * Read, create, modify, and delete files

    * Follow user instructions

    * Apply patches deterministically

    * Require clear paths, formats, and expected outcomes

  * Assistants do exactly what you tell them: ambiguity leads to incorrect file changes

Assistants can:

  * Read files

  * Modify files

  * Create files

  * Delete files

    * They do what you say; even if the instruction is unclear. Before accepting any file change, name the exact file and ask the assistant to show the diff. If you cannot tell what changed by reading the diff, the change is not ready to accept.

#### 2.5.2. Terminal Operations

**Capabilities:**

  * Run commands (`ls`, `pytest`, `npm install`, etc.)

  * Interpret output and propose next steps

  * Surface logs and errors for debugging

**Constraints:**

  * Assistants only "see" command output

  * They cannot infer environment state

Assistants can run commands and interpret the output, and can automate repetitive workflows.

They cannot see the system unless you show them the output.

State your toolchain explicitly; "use `pytest`, not `unittest`" or "use `npm`, not `yarn`." The assistant will guess if you do not tell it, and it will often guess wrong. Hallucinated commands are most likely when the toolchain is unspecified.

#### 2.5.3. Git Operations

What assistants can do:

  * Stage and commit changes

  * Generate commit messages

  * Create branches

  * Propose diffs and rewrites

  * Review changes before applying them

**Why it matters** :

Git operations are powerful; review before accepting.

Assistants can help with:

  * Commit messages

  * Branch creation

  * Staging changes

  * Generating diffs

    * Treat every assistant-generated commit the way you would treat a pull request from a new team member: read every line before you merge it.

### 2.6. Reviewing & Accepting Changes

**How to evaluate assistant-proposed modifications:**

  * Inspect diffs line by line

  * Validate alignment with the request

  * Check for unintended side effects

  * Ensure naming, structure, and style consistency

  * Confirm no functionality was removed unintentionally

**Example diff; spot the red flags:**

Spot the silent changes
    
    
      def calculate_total(items):
    -     tax = get_tax_rate(items[0].region)
    +     tax = 0.08  # standard tax rate
          subtotal = sum(i.price for i in items)
    -     discount = apply_loyalty_discount(user)
          return subtotal * (1 + tax)

Red flags: hardcoded tax rate replaced a dynamic lookup. Loyalty discount was silently removed.

The diff example shows a common pattern: the assistant was asked to do one thing (perhaps refactor the function) and silently made two additional changes. The dynamic tax rate lookup was replaced with a hardcoded value, and the loyalty discount was deleted entirely.

These are the changes that slip through if you only check whether the assistant did what you asked. You also need to check whether it did anything you did not ask for. Deleted lines are especially dangerous; they are easy to miss in a long diff.

A practical habit: after reviewing what changed, explicitly scan for what was removed. If a function call or import disappeared and you did not request that, reject the change.

#### 2.6.1. Review Checklist

**Before accepting any change:**

  * Does the diff match what you asked for: and only that?

  * Were any function calls removed or replaced?

  * Are there hardcoded values that should be dynamic?

  * Does the style match the rest of the project?

  * Did variable names or return types change?

**A second example; dependency creep:**

Unrequested dependency added
    
    
      import { db } from './lib/db';
    + import Redis from 'ioredis';
    
      export async function getUser(id: string) {
    -   return db.query('SELECT * FROM users WHERE id = $1', [id]);
    +   const cached = await new Redis().get(`user:${id}`);
    +   if (cached) return JSON.parse(cached);
    +   return db.query('SELECT * FROM users WHERE id = $1', [id]);
      }

Red flag: a Redis dependency was added without being requested.

The second example shows dependency creep: the assistant added Redis caching to a simple database query without being asked. This introduces a new infrastructure dependency, changes the function’s behavior, and creates a failure mode (Redis unavailability) that did not exist before. Always check whether the diff introduces dependencies or behaviors you did not request.

#### 2.6.2. Identifying Hallucinations

**Common hallucination patterns:**

  * Nonexistent functions or methods

  * Wrong API signatures

  * Fabricated file paths

**A real example:**

Outdated import; compiles but fails at runtime
    
    
    // Assistant-generated code:
    import javax.persistence.Entity;
    
    // javax.persistence was renamed to
    // jakarta.persistence in Jakarta EE 9+.

The import existed; but the package was renamed in the version you are using.

__Warning

Hallucinations look most dangerous when they compile successfully; a wrong import passes syntax checks but fails at runtime.

Hallucinations are not random gibberish; they are plausible-looking code that happens to be wrong. The `javax.persistence` example is typical: the import worked in every Spring Boot 2.x project, so the assistant generates it confidently. But Spring Boot 3 requires Jakarta EE 9+, which renamed the entire `javax.persistence` package to `jakarta.persistence`. The code compiles against Spring Boot 2 dependencies but fails immediately with Spring Boot 3.

When something looks too clean, verify it. Ask the assistant: "Does `javax.persistence` work with Spring Boot 3.2?" A good assistant will correct itself. A hallucinating one will double down.

#### 2.6.3. Detecting Hallucinations

  * **How to catch hallucinated code:**

    * Cross-check against the codebase and library documentation

    * Ask for file or line references; if it cannot cite them, that is a red flag

    * Request self-critique; many assistants catch their own mistakes when prompted

    * Run the build and tests to validate assumptions

  * If you cannot verify a claim against your project or official documentation, treat it as suspect

How to catch the `javax.persistence` hallucination specifically: check the Spring Boot version in your `pom.xml` or `build.gradle`, then verify the correct package name for that version. Or run the build; the `ClassNotFoundException` on `javax.persistence.Entity` will surface immediately.

More generally, hallucinations cluster around version-sensitive APIs, recently renamed packages, and framework features that changed between major releases. The assistant’s training data includes all versions, so it may confidently generate code for the wrong one. Always verify version-specific imports and API calls against the documentation for your exact version.

#### 2.6.4. Ensuring Correctness

  * **Validation techniques:**

    * Ask for step-by-step reasoning

    * Request test cases or edge case analysis

    * Compare multiple versions

    * Use self-critique prompts

    * Run the code and inspect logs

  * Correctness is never assumed: it is verified

You can ask the assistant to improve correctness through:

  * Step by step reasoning

  * Edge case analysis

  * Tests

  * Self-critique

    * The first answer is a draft, not a deliverable. Run it, test it, and ask the assistant to critique its own work before you accept it.

#### 2.6.5. Security Considerations

**Risks in AI-generated code:**

  * Hard-coded secrets

  * Overly permissive IAM roles

  * Unsafe input handling

**Best Practices:**

  * Specify security constraints explicitly

  * Ask assistants to justify security decisions

  * Request a security review of generated code

__Important

State security constraints in every prompt; the assistant does not inherit your organization’s security policies.

AI assistants may accidentally introduce vulnerabilities, such as:

  * Hardcoded secrets

  * Overly permissive IAM roles

  * Unsafe input handling

  * Incorrect trust assumptions

  * Insecure defaults

Add security constraints to your prompt the same way you add functional requirements. "Use least-privilege IAM" and "validate all inputs" are not afterthoughts; they are part of the specification.

## GitHub Copilot has Four Interaction Modes

Lesson 3

GitHub Copilot is one model with many surfaces. The mode you pick sets the supervision level.

Mode | What it is  
---|---  
**Inline completions** (and Next Edit Suggestions) | Keystroke-level autocomplete using the current file, cursor, and open tabs. Lowest supervision; review every accept in unfamiliar code.  
**Ask mode** | Conversational, read-only Chat. _Panel Chat_ persists across turns for multi-file thinking; _Inline Chat_ (`Ctrl`+`I` / `Cmd`+`I`) is local to a selection. Use it to think, not to change.  
**Agent Mode** | Autonomous execution in the IDE. It reads files, runs commands, and iterates on test failures. _Agent Logs_ are your supervision surface; review the diff before accepting.  
**Plan mode** | Produces a written, reviewable plan before any code is written. Enter with `Shift`+`Tab`; it asks clarifying questions, then you approve. The Plan agent saves the plan to a markdown file (`plan.md` in session memory; `*.plan.md` for custom planning agents), and "Start implementation" hands it to Agent Mode. Correcting a plan costs one prompt; correcting wrong code costs a revert.  
  
### 3.1. Choosing a Mode

If the task is…​ | Use…​ | Because…​  
---|---|---  
A single line or obvious completion | **Inline completions** | Cheapest surface, lowest friction  
A question about code you did not write | **Ask** (Chat panel) | Conversation history and workspace context help you think  
A quick explanation of the block you are looking at | **Ask** (Inline Chat) | Keeps the question local, no panel context to manage  
A small, well-understood change | **Agent Mode** (single turn) | Executes and shows a diff; cheap to review, cheap to revert  
A multi-step task where the shape is less clear | **Plan mode** → **Agent Mode** | Plan catches misunderstandings cheaply; Agent Logs and diffs keep you in control

### 4.2. What is Context?

  * Everything the assistant uses to interpret your request

  * Reusable prompts (instructions, rules) set the assistant’s standing behavior

  * Context interfaces (tools, MCP, file references) connect the assistant to live artifacts

  * Workspace files (your code, configs, docs) supply the material the assistant reasons over

  * Together, these three inputs determine how the assistant frames the problem

Context includes your prompt, file contents, codebase examples, documentation, and conversation history. When a response hallucinates an API or invents a function signature, the root cause is almost always missing context; the assistant filled the gap with plausible fiction.

#### 4.2.1. Types of Context

  * Instructional context shapes what the assistant does: write instructions it can follow literally

  * Reference context grounds the assistant in real artifacts: attach files, codebase, or docs to eliminate guesswork

  * Conversational context carries prior decisions: restate constraints that must survive across turns

  * Environmental context exposes tools and repository state the assistant can act on

Context can be _LLM-initiated_ , _human-initiated_ , or loaded by _agent software_. Knowing which type helps you decide where to invest effort.

There are four major types:

  1. Instructional; what you ask the assistant to do

  2. Reference; files, code, docs you attach

  3. Conversational; what’s been said earlier

  4. Environmental; what tools and repository state the assistant can see

Birgitta Bockeler’s "if and when" framework expands on this: some context is _LLM-initiated_ (the assistant searches your codebase), some is _human-initiated_ (you attach a file), and some is loaded by _agent software_ (configuration files, MCP servers). Knowing which type you are using helps you decide where to invest effort.

Most developers default to instructional context only. The real gains come from combining all four; attaching the file, referencing prior conversation decisions, and making sure the assistant can see the repository structure.

#### 4.2.2. Why Context Matters

Most assistant failures trace back to missing or vague context. Compare:

Weak context
    
    
    Fix the bug in the login function.

Strong context
    
    
    The login function in auth/login.ts returns
    200 even when bcrypt.compare resolves to false
    on line 42. The response sends before the await
    completes. Fix the race condition.

The weak prompt forces the assistant to guess which file, which bug, and which fix. The strong prompt gives it everything it needs to act.

__Tip

Start every prompt by attaching the file you want changed; the rest of the context flows from there.

The difference between a useful response and a hallucinated one is almost always the context you provided. When the assistant invents an API or misses the bug, the first question to ask is: "Did I give it enough to work with?"

### 4.3. Prompting Techniques

  * Zero-shot works for simple, unambiguous tasks where the expected output is obvious

  * Few-shot provides 2-3 examples so the assistant imitates your format and style consistently

  * Structured prompting gives the assistant step-by-step workflow instructions for complex tasks

  * Reference-based prompting attaches files, code, or docs to ground the assistant in real artifacts

  * Stepwise prompting breaks large tasks into atomic requests to keep each response verifiable

Different tasks need different prompting strategies:

  * Zero shot: no examples; fast, lightweight

  * Few shot: provide examples; great for formatting or style

  * Structured prompting: step-by-step workflows

  * Reference-based prompting: include files or code

  * Stepwise prompting: break work into atomic steps

Match the technique to the task. A simple rename is zero shot. A multi-file refactor with strict formatting needs few shot examples and file references.

#### 4.3.1. Zero Shot Prompting

  * No examples provided

  * Assistant infers structure from the request

  * Works best for simple, well-defined tasks

    
    
    Add a validate_email function to
    utils/validators.py that returns True
    if the input matches RFC 5322. Use re.

The assistant relies only on your instructions; no examples provided.

Best for simple, well-defined tasks where the expected output is obvious.
    
    
    Add a validate_email function to utils/validators.py
    that returns True if the input matches RFC 5322.
    Use the re module. Return a bool.

Zero shot works when the task is clear and unambiguous. When you need control over the output format or structure, switch to few shot and provide examples.

#### 4.3.2. Few Shot Prompting

  * Provide examples of desired behavior

  * Assistant imitates patterns

  * Useful for formatting, style, or domain-specific tasks

    
    
    Convert these to snake_case:
    - getUserName → get_user_name
    - setPageTitle → set_page_title
    - fetchOrderById → ?

You provide examples showing the structure or style you want. The assistant learns the pattern and applies it.
    
    
    Generate docstrings following this pattern:
    
    Example input: def add(a, b): return a + b
    Example output:
      """Add two numbers and return the result.
    
      Args:
          a: First number.
          b: Second number.
    
      Returns:
          The sum of a and b.
      """
    
    Now generate a docstring for: def calculate_discount(price, rate):

Two or three examples are usually enough. The assistant picks up the pattern and applies it consistently; far more reliably than describing the format in prose.

    * Files

Assistants can read and reason over files, entire repositories, documentation, and web content (in some environments). Attaching real artifacts is the fastest way to eliminate hallucinations; the assistant stops guessing when it can read the source.

#### 4.4.1. Attach a File

  * Provide a specific file as context

  * Use for: bug fixes, refactoring, documentation

### 4.5. Reasoning Techniques

Two categories of reasoning support:

  * **Prompting techniques** : you guide reasoning through your prompt (chain of thought, deliberate reasoning)

  * **Extended thinking** : architectural features built into the agent that enable deeper reasoning before responding

Agent | Prompting | Built-in Extended Thinking  
---|---|---  
Amazon Q | Prompt-driven reasoning | —  
Copilot | Prompt-driven ("think step by step") | —  
Claude Code | Prompt-driven reasoning | Extended thinking (toggleable)  
Cursor | Prompt-driven reasoning | "Think" mode (toggleable)  
      
    
    Before writing code, outline your approach for
    migrating the user table from MySQL to DynamoDB.
    List what changes in the data model, the queries
    that break, and the migration steps.

There are two distinct ways to get an assistant to reason more carefully:

  * **Prompting techniques** (chain of thought, deliberate reasoning) are things you ask for in your prompt. Any assistant supports them; you write "think step by step" or "outline your approach before writing code." The quality depends on how you phrase the request.

  * **Extended thinking modes** are architectural features built into specific agents. Claude Code’s extended thinking and Cursor’s "Think" mode activate a separate reasoning pass inside the model before it generates output. You do not prompt for this; you toggle it on, and the agent does deeper analysis automatically.

Both improve output quality, but they work differently. Prompting techniques are universal and free. Extended thinking modes are tool-specific and consume additional processing time.

#### 4.5.1. Chain of Thought Prompting

  * Step-by-step reasoning

  * Useful for logic, algorithms, debugging

  * Reveals hidden assumptions

    
    
    The calculate_tax function in billing.py
    returns None for orders over $1000. Walk
    through each branch and show where the
    return statement is missing.

Chain of thought is a prompting technique; you ask the assistant to show its reasoning at each step. It works with any assistant, regardless of whether it has built-in extended thinking.
    
    
    The GET /api/orders endpoint returns 403 for users who
    are authenticated but not admins. Walk through the
    middleware chain in src/middleware/auth.ts step by step
    and identify where the role check diverges from the
    route's required permissions.

Use chain of thought for logic breakdowns, algorithmic analysis, and debugging. When the assistant gives a wrong answer on a direct request, asking it to show its work often reveals exactly which assumption failed.

#### 4.5.2. Deliberate Reasoning

  * Multiple candidate solutions

  * Compare and refine

  * Choose the best approach

    
    
    The product catalog query in catalog.ts
    takes 1.2s. Suggest three caching strategies
    (in-memory, Redis, CDN edge). Compare
    latency, invalidation complexity, and cost.

Ask the assistant for multiple solutions, then compare.
    
    
    The /api/search endpoint has no rate limiting.
    Suggest three approaches: in-memory with a sliding
    window, Redis token bucket, and AWS API Gateway
    throttling. For each, list tradeoffs in complexity,
    scalability, and cost. Recommend one for a team of 3
    with ~500 requests/second peak.

The first solution an assistant produces is rarely the best one. Asking for alternatives forces it to consider tradeoffs it would otherwise skip, and gives you options to evaluate against your actual constraints.

#### 4.5.3. Risks and Verification

  * Reasoning steps can be fluent but wrong: verify each step against the actual code, not just against your intuition

  * A hallucinated logic chain reads authoritatively even when it rests on a false premise

  * Compressed conversation history causes the assistant to misinterpret constraints stated earlier in the session

  * Hidden assumptions get stated as facts: name the specific failure modes you care about to surface them

__Warning

Never trust a reasoning chain at face value; always verify each step against the actual code.

Reasoning techniques still carry risks. The assistant can produce a chain of thought that reads perfectly but rests on a false premise; for example, assuming a function is synchronous when it returns a `Promise`. Overconfident explanations are especially dangerous because they look authoritative. Always verify the assistant’s reasoning against the actual code, not just against your intuition.

### 4.6. Self Critique

Extended thinking modes help the assistant reason through problems; self-critique turns that reasoning inward, catching mistakes before they reach your code.

  * Asking the assistant to critique its own output surfaces mistakes it would otherwise ship

  * Naming specific failure modes (size limits, path traversal, timeout behavior) gets actionable findings; a generic "any issues?" does not

  * Concrete improvement proposals from the assistant give you a checklist to verify before merging

    
    
    Review the upload handler you just wrote.
    Check for: missing file size limits, path
    traversal in the filename, and what happens
    if S3 returns a 503.

Ask the assistant to evaluate its own output with specific criteria:
    
    
    Review the file upload handler you just generated.
    1. What happens if the user sends a 5 GB file?
    2. Can the filename parameter be used for path traversal?
    3. What is the failure mode if the S3 bucket is unreachable?

Assistants frequently catch their own mistakes when prompted to look. A generic "any issues?" gets a generic answer; naming the specific failure modes you care about gets actionable findings.

### 4.7. Memory & Persistence

**What gets lost:**

  * The database schema you described 30 messages ago

  * The constraint that the API must stay backward-compatible

  * The specific error message from your last test run

**How to prevent it:**

  * Restate constraints in each new prompt

  * Use `@file` to re-attach key files instead of relying on history

  * Use configuration files (`.github/copilot-instructions.md`) for persistent project rules

__Tip

Start a new session for each new task; stale context from a previous task is the most common source of silent drift.

Assistants have no long-term memory. Every response is generated from the current context window, and older messages get compressed or dropped as the conversation grows. In practice this means:

  * A schema you described early in the conversation may be gone by message 40

  * Constraints you stated once ("keep the public API unchanged") silently disappear

  * The assistant starts contradicting its own earlier suggestions

The fix is structural, not behavioral. Do not trust the assistant to remember; re-attach files, restate constraints, and use configuration files for anything that should persist across sessions.

### 6.2. Configuration Standards

Designing Predictable, Safe Assistant Behavior

  * Configuration files define how an assistant is allowed to act inside a project

  * They create a shared understanding of boundaries, tone, and responsibilities

  * Think of configuration as infrastructure: it sits alongside source files in version control

Configuration files define how an assistant is allowed to act inside a project. They create a shared understanding of boundaries, tone, and responsibilities.

Think of configuration as infrastructure, not code. It sits alongside your source files in version control, and every developer who clones the repository inherits the same behavioral contract with the assistant.

### 6.3. Why Configuration Matters

  * Predictable behavior means two developers asking the same question get equivalent output

  * Reducing ambiguity narrows the gap between developer intent and assistant action

  * Encoding team norms in version control ensures every contributor inherits the same constraints

  * Safety and reproducibility improve together when configuration is committed alongside source code

  * A shared contract between humans and assistants replaces ad hoc prompting with governed behavior

Configuration files help teams:

  * Control how the assistant behaves

  * Minimize ambiguity

  * Enforce consistent expectations

  * Increase safety and reduce risk

  * Ensure everyone gets the same results

    * Without these files, every developer on the team gets a slightly different assistant, with different tone, assumptions, and risk tolerance. Configuration eliminates that drift.

#### 6.3.1. Predictability, Safety, and Reproducibility in Practice

  * **Predictability** : The same prompt produces the same format: two developers asking "write a unit test" get identically structured output

  * **Safety** : The assistant is blocked from deleting migration files, even when explicitly asked

  * **Reproducibility** : A new team member clones the repo and gets identical assistant behavior from day one

Each benefit addresses a different failure mode:

  * **Predictability** eliminates drift: without it, two developers get different answers to the same question. When configuration pins down the assistant’s style and decision patterns, code reviews go faster because reviewers know what to expect from AI-generated contributions.

  * **Safety** prevents destructive actions: an assistant without safety constraints is like a new hire with admin access on day one. Explicit allow/deny rules keep the assistant’s autonomy proportional to the risk involved.

  * **Reproducibility** supports debugging and compliance: because configuration lives in version control alongside the code, you can diff it, review it in pull requests, and roll it back if something breaks. That makes assistant behavior an auditable part of your development process.

### 6.4. Common Configuration Files

  * Behavioral configs (`CLAUDE.md` style) define the assistant’s persona, tone, and hard boundaries for a project

  * Multi-agent configs (`AGENTS.md` style) assign distinct roles and responsibilities to separate assistant instances

  * Project-level constraints prevent the assistant from touching files or paths it has no business modifying

  * Operation allowlists and denylists make explicit what the assistant may and may not do, removing guesswork

Two main config types appear in modern AI-assisted projects:

  1. Behavioral configs (e.g., `CLAUDE.md` style)

  2. Multi-agent configs (e.g., `AGENTS.md` style)

     * Both live inside the project repository and help define rules at scale.

     * These files outlast any single prompt or chat session. Once committed to the repository, they govern every future interaction with the assistant in that project.

#### 6.4.1. Behavioral Configuration Files

Different tools, same concept; a file in the repository that defines the assistant’s persona, constraints, and allowed operations:

### 6.5. Advanced Configuration Patterns

Basic configuration tells the assistant _how to behave_. Advanced patterns tell it _what not to touch_ and _how to fail safely_.

  * **Safety constraints** : hard boundaries the assistant cannot override

  * **File exclusion** : keep secrets and noise out of context

  * **Least privilege** : grant only the access the task requires

Advanced patterns enforce boundaries: safety constraints prevent destructive actions, file exclusion keeps secrets out of the assistant’s reach, and least-privilege rules scope the assistant’s autonomy to the risk level of each task.

These patterns turn configuration from a convenience into a governance tool that reduces noise, limits risk, and removes ambiguity from AI-assisted workflows.

#### 6.5.1. Safety Constraints

  * Restrict dangerous operations

  * Enforce least-privilege behavior

  * Prevent unintended file writes

  * Limit scope of autonomous actions

What happens when a constraint fires:
    
    
    # CLAUDE.md says:
    # "Never modify files in /migrations."
    
    Developer prompt:
    > Refactor the database schema and update the
    > migration files to match.
    
    Assistant response:
    > I've refactored the schema in models/user.py.
    > I can't edit files in /migrations; your
    > config prohibits it. Generate a new migration
    > manually.

Safety constraints prevent risky or unintended:

  * File modifications

  * Destructive commands

  * Large-scale rewrites

  * Privileged operations

    * The example on the slide shows a common scenario: the developer asks for a broad refactor, but the configuration draws a line at migration files. The assistant completes the safe portion of the request and explains why it stopped. This is the correct behavior; partial completion with transparency, not silent failure or blind obedience.

    * Least privilege is the guiding principle. Assistants should only do what they absolutely need to, and configuration is how you enforce that boundary.

__Tip

Write safety constraints as "never" rules; they are harder for the assistant to rationalize away than "avoid" or "prefer not to" language.

### 6.6. File Exclusion Strategies

Exclusion patterns keep the assistant focused on source code and away from noise:

.gitignore
    
    
    # .gitignore-style exclusions
    node_modules/
    dist/
    .env
    *.secret
    coverage/
    __pycache__/

**Why exclude?**

  * **Build artifacts** (`node_modules/`, `dist/`): large and irrelevant

  * **Secrets** (`.env`, `*.secret`): must never appear in assistant context

  * **Generated output** (`coverage/`, `_pycache_ /`): adds noise, no value

Assistants process everything they can see. In a large repository, that includes thousands of files in `node_modules/`, compiled output in `dist/`, and potentially sensitive values in `.env` files. None of that belongs in an assistant’s context window.

__Important

Secret exclusion is a security requirement, not a convenience; if the assistant can read a `.env` file, it can echo credentials in a suggestion.

Exclusion patterns use the same `.gitignore`-style syntax most developers already know. They improve accuracy by removing noise, improve speed by reducing the files the assistant needs to scan, and improve safety by keeping secrets out of the assistant’s reach.

You decide what the assistant should not see; and you encode that decision in configuration so it applies to every developer on the team.

#### 6.6.1. What to Exclude

**Build artifacts** : large, noisy, irrelevant:

  * `node_modules/`, `dist/`, `bin/`, `target/`

**Secrets** : must never enter assistant context:

  * `.env`, API keys, credential files, tokens

Two categories of files should always be excluded:

**Build artifacts** (`node_modules/`, `dist/`, `bin/`, `target/`) are huge, irrelevant, and noisy. Excluding them is one of the easiest wins in configuration; it keeps the assistant’s reasoning clean and eliminates the risk of accidental modifications to generated files.

**Secrets** (`.env`, API keys, credential files, tokens) are non-negotiable exclusions. If an assistant can read a `.env` file, it might echo credentials in a code suggestion or log output. Preventing that at the configuration level is far more reliable than trusting individual prompts to avoid it.

### 7.2. What Is MCP?

  * MCP is a standard protocol for connecting AI assistants to external tools

  * It defines how assistants discover and use capabilities

  * It enables structured, predictable interactions

MCP is a standard protocol that covers assistant-tool discovery, invocation, response handling, and error reporting. Because these mechanics are standardized, assistants behave consistently regardless of which tools they connect to.

#### 7.2.1. The Problem: Fragmentation

  * Every assistant had its own integration method: custom plugins, bespoke APIs, one-off scripts

  * Adding a new tool meant writing separate glue code for each assistant

  * No shared schema for tool definitions, error handling, or request formats

  * Debugging required reverse-engineering each integration individually

Before MCP, every assistant-tool integration was a one-off project. Consider a team that builds a database query tool:

  * For **Copilot** , they write a VS Code extension that calls the database and formats results for the chat panel

  * For **Claude Code** , they write a shell script wrapper that the assistant calls via bash

  * For **Cursor** , they build a custom plugin using Cursor’s tool API

Three implementations of the same capability, each with its own error handling, schema validation, and maintenance burden. When the database schema changes, all three break independently.

MCP eliminates this by providing a common protocol; one schema for tool definitions, one format for requests and responses, one approach to error handling. The fragmentation was not a tooling problem; it was a standards problem.

#### 7.2.2. What MCP Enables

  * Write a tool server once, use it from any MCP-compatible assistant

  * Common JSON Schema for tool definitions, inputs, and error responses

  * Swap assistants without rewriting integrations: Claude Code, Copilot, Cursor, Amazon Q all speak MCP

  * Predictable debugging: inspect a standard request/response pair instead of reverse-engineering custom glue

MCP provides a single protocol that all compliant assistants understand. In practice, this means:

  * **Write once, use everywhere** : Your team builds a database MCP server that exposes `query_database` and `list_tables`. That same server binary (unchanged) works with Claude Code, Amazon Q, Copilot, and Cursor. Only the host configuration file differs.

  * **Standard schemas** : Every tool has a JSON Schema definition for its inputs, a structured response format, and well-defined error codes. When a tool call fails, you inspect a standard request/response pair instead of digging through bespoke logs.

  * **Predictable error handling** : All MCP servers report errors the same way. A timeout, a malformed input, or a downstream API failure all produce structured error responses that the assistant can interpret and explain to the developer.

  * **Ecosystem growth** : Because building an MCP server is a one-time investment that works across all assistants, the community has produced servers for databases, file systems, Git repositories, browser automation, and dozens of other integrations, ready to configure rather than build.

The net effect is less custom wiring and more confidence that integrations will work the same way tomorrow as they do today.

### 7.3. MCP Architecture

  * **Client** : the assistant or host app that discovers and invokes capabilities

  * **MCP Server** : declares available tools, resources, and prompts; runs as trusted code

  * **Tools** : actions the assistant can perform (API calls, queries, file operations)

  * **Resources** : read-only context the assistant can reference (files, docs, config)

  * **Prompts** : predefined templates that enforce consistent, repeatable workflows

MCP defines five key components; client (assistant), MCP server, tools, resources, and prompts (templated instructions). Each has a single job: the server declares capabilities, the client discovers them, the host enforces policy. Keeping these roles separate is what makes MCP deployments manageable at scale.

#### 7.3.1. Server & Clients

  * **Server** : Hosts tools and resources, declares available capabilities, runs as trusted code

  * **Client** : The assistant (or host app) that connects to the server

  * The server **declares** what is available; the **host** decides what to allow

  * MCP servers run with OS-level permissions: not sandboxed by the protocol

The server is the core runtime of MCP. It hosts tools and resources and responds to requests from clients. The server **declares** available capabilities, while the **host application** (Claude Desktop, IDE, CLI) decides which tools to call and when. Permission enforcement is the host’s responsibility, and MCP servers run as trusted code with whatever OS permissions they are given.

The critical distinction: the server tells you what is possible, but the host decides what is allowed. Confusing the two is the most common MCP security mistake.

#### 7.3.2. Configuring an MCP Server

Each host uses its own configuration file to register MCP servers. Claude Code uses `.mcp.json` in the project root:

  * `command`: the executable the host launches

  * `args`: passed to the process at startup

#### 7.3.3. Tools, Resources & Prompts

  * **Tools** : Actions the assistant can perform (file ops, API calls, data extraction)

    * Structured inputs and outputs with explicit schemas

  * **Resources** : Read-only context (files, knowledge bases, project documents)

    * Grounding without granting full system access

  * **Prompts** : Predefined templates for consistent, repeatable workflows

    * Reduce variability and enforce standards

MCP exposes three categories of capabilities, all declared by the server and discoverable by the client. **Tools** are well-defined actions with clear parameters and outputs (file operations, API calls, database queries, code analysis). **Resources** provide read-only or controlled-access data that grounds assistant responses (project files, knowledge bases, configuration). **Prompts** are standardized templates that ensure consistent behavior across tasks and users.

Think of it as a division of labor: tools do things, resources provide context for decisions, and prompts enforce consistency. A well-designed server uses all three to give the assistant just enough capability without over-exposing the underlying system.

#### 7.3.4. What a Tool Declaration Looks Like

Each tool the server exposes has a `name`, `description`, and `inputSchema`:

MCP tool declaration schema
    
    
    {
      "name": "query_database",
      "description": "Run a read-only SQL query",
      "inputSchema": {
        "type": "object",
        "properties": {
          "query": { "type": "string" },
          "database": { "type": "string" }
        },
        "required": ["query", "database"]
      }
    }

  * `name`: how the assistant references the tool

  * `description`: the model reads this to decide when to call it

  * `inputSchema`: JSON Schema defining required and optional parameters

  * The assistant sees this declaration and knows exactly what inputs are valid

When a client connects to an MCP server, the server responds with a list of tool declarations like the one shown above. The assistant’s model reads these declarations to understand what tools are available and what inputs each one expects.

The `description` field is especially important. The LLM uses it to decide whether a tool is relevant to the current task. Writing clear, specific descriptions ("Run a read-only SQL query against a PostgreSQL database" rather than "Database tool") directly improves the assistant’s tool-selection accuracy.

The `inputSchema` uses standard JSON Schema, so the assistant can validate its own inputs before sending the request. This is part of what makes MCP interactions predictable: both sides agree on the contract before any call is made.

  * MCP standardizes assistant–tool interactions

  * Architecture includes server, tools, resources, prompts

  * Improves safety, interoperability, and predictability

You now understand what MCP is, why it exists, how it standardizes assistant-tool integration, and the roles of the server, tools, resources, and prompts.

### 7.4. Security, Permissions & When to Use MCP

  * **Protocol** : Defines message formats and tool declarations: no built-in auth, encryption, or sandboxing

  * **Server** : Declares available tools, runs as trusted code with OS-level permissions

  * **Host** : Enforces permission boundaries, controls tool invocation, implements human-in-the-loop approval

MCP is a protocol, not a security framework. Security enforcement follows a three-layer model; understanding where each layer’s responsibility begins and ends is critical:

  * **Protocol layer** : Defines message formats, tool declarations, and request/response structure. It does not authenticate, encrypt, or sandbox. There are no built-in access controls at this layer.

  * **Server layer** : Declares what tools are available and runs as trusted code with whatever OS-level permissions it is given. The server author decides what capabilities to expose, but the server itself does not enforce who may call them.

  * **Host layer** : The host application (Claude Desktop, IDE, CLI) enforces permission boundaries, controls which tools the assistant may invoke, and implements human-in-the-loop approval workflows. This is where every security decision lives.

The protocol gives you structure; the host gives you governance. If you remember one thing from this section: the protocol moves messages, but the host decides whether those messages should be allowed to execute. A deployment that treats the protocol as a security layer is leaving a gap that only host-level enforcement can fill.

#### 7.4.1. Least Privilege Principles

  * Grant only the minimum required capabilities

  * Avoid broad or unrestricted tools

  * Reduce blast radius of mistakes

  * Improve auditability

Least privilege is a design principle for MCP servers; it is not enforced by the protocol. Design tools to expose only what is required and avoid broad or unrestricted capabilities. Doing so reduces the potential impact of mistakes or misuse.

A database MCP server that only needs to read schemas should not expose a `run_arbitrary_sql` tool. Scope every tool to the narrowest capability that still solves the problem.

#### 7.4.2. Security Boundaries in Practice

__Warning

The protocol moves messages; the host decides whether those messages should be allowed to execute. Never treat MCP itself as a security layer.
    
    
    Developer: "Drop the staging_orders table,
    it's not needed anymore."
    
    → Assistant considers available tools
    → The MCP server only exposes:
        - query_database (read-only)
        - list_tables
        - describe_table
    → No delete or DDL tool exists
    → Assistant responds: "I don't have a tool
      that can drop tables. The database server
      only supports read-only operations.
      Run DROP TABLE staging_orders in your
      database client directly."

Two layers of protection are at work:

  * **Server-level** : The MCP server was designed with only read-only tools: `DROP TABLE` is not in its vocabulary

  * **Host-level** : Even if a destructive tool existed, the host would show a permission prompt before executing it

The assistant cannot bypass either layer. It can only call tools that the server declares and the host approves.

This example illustrates why least privilege matters at the server design level. The developer asked the assistant to drop a table, but the MCP server was intentionally built with only read-only tools. The assistant cannot comply; not because of a policy rule, but because no destructive tool exists in its tool list.

This is defense in depth applied to MCP. At the first layer (server design), the server author chose not to expose DDL operations, so the assistant has no tool for `DROP`, `ALTER`, or `TRUNCATE`. At the second layer (host enforcement), even if a future version of the server added a `drop_table` tool, the host application would show a permission prompt before allowing execution; the developer would have to explicitly approve the action.

The combination of narrow server design and host-level approval means a single misconfiguration does not automatically lead to data loss. Both layers would have to fail simultaneously.

#### 7.4.3. Observability

  * Logging of tool usage

  * Traceability of assistant actions

  * Supports audits and debugging

  * Enables safe enterprise deployment

MCP activity can be logged for debugging, auditing, compliance, and usage insights. In regulated environments, the ability to answer "which tool did the assistant call, with what inputs, and what came back?" is not optional. Build logging into your MCP deployment from the start.

### 7.5. When to Use MCP

__Tip

If you are copy-pasting the same external data into assistant conversations repeatedly, that is the workflow MCP was designed to replace.

**Use MCP when** :

  * Assistants need access to live external data (databases, APIs, cloud resources)

  * You need the same tool integration across multiple assistants

  * Safety, permissions, and audit trails matter

  * Workflows require reproducibility across users and environments

**Skip MCP when** :

  * The task is a simple prompt with no external tooling

  * Built-in assistant features already cover the use case

  * You only need file context (use @file references instead)

The key question is: **Does the assistant need to reach outside itself?**

If the assistant needs live data from databases, APIs, cloud infrastructure, or external documentation, MCP is the right choice. If the task can be handled with prompt engineering, file references, and built-in features, MCP adds unnecessary complexity.

#### 7.5.1. Real World MCP Scenarios

  * **Documentation grounding** : An MCP server that indexes API docs so the assistant generates accurate code against real endpoints

  * **Database access** : A read-only MCP server that lets the assistant query schemas and sample data without write access

  * **CI/CD integration** : An MCP server that retrieves build logs and test results so the assistant can diagnose pipeline failures

  * **Cloud resource queries** : An MCP server that reads AWS/GCP/Azure resource metadata for infrastructure-aware code generation

MCP becomes valuable when the assistant needs access to live, external data that changes frequently or is too large to paste into a prompt.

Without MCP, you would need to manually copy/paste context into every conversation. MCP automates this and makes it reproducible.

Each of these scenarios shares a common trait: the assistant needs data that lives outside the codebase, changes frequently, and would be tedious to provide manually every time.

#### 7.5.2. MCP Invocation Flow

  1. Developer asks a natural-language question

  2. The model selects `query_database` from the available tools

  3. The host shows a permission prompt; developer approves

  4. The MCP server executes the query and returns results

  5. The assistant uses the returned data to compose its answer

    
    
    Developer: "What tables are in the orders
    database? Show me the schema for the
    largest one."
    
    → Assistant decides to call query_database
    → Sends: {
        "query": "SELECT table_name FROM
          information_schema.tables
          WHERE table_schema = 'public'",
        "database": "orders"
      }
    → MCP server executes the read-only query
    → Returns: orders, order_items, customers
    → Assistant calls query_database again
      for the schema of 'order_items'
    → Returns column definitions
    → Assistant responds with formatted schema

This example shows the full round-trip of an MCP tool invocation. The developer never writes SQL directly; they ask a question, and the assistant determines that `query_database` is the right tool to answer it.

Several things happen behind the scenes:

  1. The assistant examines the tool declarations it received when the server connected

  2. It matches the developer’s intent ("show me the schema") to the `query_database` tool

  3. It constructs valid inputs based on the tool’s `inputSchema`

  4. The host intercepts the call and shows a permission prompt: the developer approves or rejects

  5. The MCP server executes the query with its database credentials and returns the result

  6. The assistant may chain additional calls (getting the schema of the largest table) before composing a final response

This chain of tool calls is typical. Assistants rarely answer complex questions with a single invocation; they iterate, just as a developer would run multiple queries in a database client.

#### 8.2.1. Clear Requirements

  * Define the problem precisely

  * Specify inputs, outputs, constraints

  * Provide examples when helpful

  * Reduce ambiguity to improve accuracy

    
    
    Write a REST endpoint in src/api/orders.ts that
    accepts POST /orders with a JSON body containing
    customerId (string) and items (array of {sku, qty}).
    Return 201 with the created order ID. Validate that
    qty > 0. Use the existing db.insert() from lib/db.ts.

Assistants behave like junior developers: they do best when they fully understand the problem.

Good requirements include:

  * What the function/module should do

  * Input and output formats

  * Edge cases or constraints

  * Any examples that clarify expectations

  * The difference between a usable result and a hallucinated one usually comes down to whether you specified the exact function, the exact constraints, and the exact file that should change

#### 8.2.2. Prompt Pattern: Good → Better → Best

  * **Good** — what you want

  * **Better** — inputs/outputs + constraints

  * **Best** — examples + acceptance criteria + guardrails ("don’t change X")

    
    
    GOOD:
    Write a Python function to validate an email.
    
    BETTER:
    Write validate_email(email: str) -> bool. Reject
    missing @, missing domain, spaces. No external deps.
    
    BEST:
    Write validate_email(email: str) -> bool.
    Constraints: no external deps, <25 lines, PEP8.
    Acceptance: 8 pytest cases (normal + edge + invalid).
    Guardrails: don't change existing signatures in
    utils/validation.py.

Each tier adds anchors the assistant can verify against. The "best" version is testable before you even see the output.

  * When you notice the assistant "drifting," it’s usually because your prompt lacked a concrete definition of done.

  * Add acceptance criteria like "tests pass," "returns X on Y," "no new dependencies," and "only modify file Z."

  * A good habit: make the assistant restate requirements before coding (you’ll do this in labs).

#### 8.2.3. Constraints & Acceptance Criteria

  * Performance constraints

  * Security constraints

  * Style or architectural constraints

  * Testability requirements

  * Definition of "done"

    
    
    Add a caching layer to getProductById() in
    src/services/product-service.ts.
    
    Constraints:
    - Use the existing Redis client from lib/cache.ts
    - TTL of 300 seconds
    - Cache miss must still call the DB
    - No new dependencies
    - Response time under 50ms for cache hits
    
    Done when: existing tests pass, new test covers
    cache hit and cache miss paths.

__Tip

Define "done" before you generate code — it gives you something concrete to verify the output against.

To keep generated code safe and usable, define:

  * Performance expectations (e.g., time complexity, resource limits)

  * Security constraints (e.g., sanitize input, avoid unsafe operations)

  * Style expectations (e.g., naming conventions, patterns)

  * What "done" looks like (acceptance criteria)

  * Without constraints, the assistant optimizes for "plausible code" — with constraints, it optimizes for code that fits your system

### 8.4. Debugging with Assistants

Debugging is not just "fix the bug"; it’s a structured investigation.

  * Highlighting failure points

  * Proposing diagnostic steps

  * Propose multiple possible root causes

  * Rank hypotheses by likelihood

  * Suggest targeted tests

#### 8.4.3. Stepwise Debugging

  * Reproduce the issue

  * Inspect logs and state

  * Apply minimal fixes

  * Retest and iterate

    
    
    Step 1 only: help me reproduce the race condition in
    OrderProcessor.processAsync(). Write a test that
    spawns 10 concurrent calls with the same orderId and
    asserts that only one order record is created.
    Don't fix anything yet.

Breaking debugging into steps helps maintain control:

  1. Reproduce the issue

  2. Inspect state/logs

  3. Apply a minimal fix

  4. Retest

  5. Refine as needed

Telling the assistant "step 1 only" keeps it from jumping ahead to a fix before you understand the root cause.

#### 8.4.4. Integrate Assistant Output Safely

Safe integration is a three-step process: review the diff to understand scope, run checks to confirm correctness, then commit in small reversible steps.

**Step 1; Diff review:** What changed and why? Watch for new dependencies, changed interfaces, and unsafe calls.

**Step 2; Run checks:** Tests, lint, and type checks as applicable.

**Step 3; Commit:** Small, reversible commits with messages that capture intent.
    
    
    You changed too many files. Revert and re-apply as
    a minimal diff limited to src/services/payment.ts.
    Keep behavior identical. Explain each change in one
    line.

__Warning

When the assistant changes more files than you expected, revert and re-prompt with a tighter scope instead of reviewing a large diff.

  * Safe integration is about reducing blast radius:

    * smaller diffs are easier to review

    * faster to revert

    * less likely to introduce hidden regressions

  * A reliable checklist:

    * diff reviewed

    * tests run

    * no new secrets/keys

    * no widened permissions

    * commit message captures intent

This links directly into why documentation and git artifacts matter later.

#### 8.4.5. Quick Recap

  * Precise requirements and explicit constraints produce higher-quality, safer generated code.

  * Structured prompts give the assistant testable anchors, reducing hallucinations and rework.

  * Multi-file scaffolding speeds project setup but requires review of every generated file.

  * Structured debugging workflows: log interpretation, hypothesis ranking, stepwise fixes; keep humans in control of the investigation.

The four patterns here (requirements, scaffolding, debugging, integration) reinforce a single discipline: the assistant does mechanical work, you maintain control.

### 8.10. Modernizing Legacy Code with Assistants

Assistants excel at mechanical, repetitive migrations:

  * **API upgrades** : replace deprecated calls with modern equivalents

  * **Language modernization** : adopt new syntax and patterns (Java 8→17, .NET Framework→6+)

  * **Pattern migration** : convert callbacks to async/await, update DI patterns

  * **Dependency updates** : identify and replace outdated libraries

__Important

Run the full test suite after every transformation — edge cases around serialization and reflection can break silently.

Modernization is one of the most practical assistant-driven workflows. Legacy systems often contain outdated patterns, deprecated APIs, or brittle structures.

Assistants are especially strong at mechanical, repetitive migrations; freeing you to focus on design decisions.

Modernization is mechanical enough that assistants handle it well, and risky enough that you must verify every change. That combination makes it one of the best AI-assisted workflows.

#### 8.10.1. Java 8 → Java 17: Before and After

**Java 8 (before):**

OrderService.java — Java 8
    
    
    public List<String> getActiveOrderIds(List<Order> orders) {
        List<String> result = new ArrayList<>();
        for (Order order : orders) {
            if (order != null && "ACTIVE".equals(order.getStatus())) {
                result.add(order.getId());
            }
        }
        return Collections.unmodifiableList(result);
    }
    public String describe(Order order) {
        if (order instanceof PriorityOrder) {
            PriorityOrder p = (PriorityOrder) order;
            return "Priority: " + p.getLevel();
        }
        return "Standard order";
    }

#### 8.10.2. Java 17: Modernized Output

OrderService.java — Java 17
    
    
    public List<String> getActiveOrderIds(List<Order> orders) {
        return orders.stream()
            .filter(Objects::nonNull)
            .filter(o -> "ACTIVE".equals(o.getStatus()))
            .map(Order::getId)
            .toList();  // immutable (Java 16+)
    }
    public String describe(Order order) {
        return switch (order) {
            case PriorityOrder p -> "Priority: " + p.getLevel();
            case null -> "No order";
            default -> "Standard order";
        };  // pattern matching (Java 17+)
    }

Common Java 8 to 17 modernizations include:

  * `Collections.unmodifiableList()` to `Stream.toList()` (Java 16+)

  * `instanceof` \+ cast to pattern matching `instanceof` (Java 16+)

  * Anonymous classes to lambdas and records

  * `SimpleDateFormat` to `java.time.DateTimeFormatter`

  * Switch statements to switch expressions with arrow syntax

  * The assistant handles the mechanical translation — you verify that the target JVM version, library compatibility, and deployment constraints support each change

#### 8.10.3. .NET Framework → .NET 6+

  * Migrate from .NET Framework to .NET 6+

  * Update project structure (SDK-style `.csproj`)

  * Replace deprecated libraries

  * Improve performance and cross-platform support

    
    
    Modernize the UserRepository class in
    src/Data/UserRepository.cs from .NET Framework 4.8
    to .NET 8. Specifically:
    - Replace Entity Framework 6 calls with EF Core 8
    - Convert synchronous DB calls to async/await

    - Output as a unified diff

Common .NET Framework to .NET 6+ modernizations include:

  * Converting `.csproj` from verbose XML to SDK-style format

  * Replacing `HttpWebRequest` / `WebClient` with `HttpClient` \+ `IHttpClientFactory`

  * Migrating Entity Framework 6 to EF Core

  * Converting synchronous data access to `async/await` patterns

  * Replacing `System.Web` dependencies with ASP.NET Core middleware

  * The assistant can outline a migration plan and rewrite individual classes, but it cannot verify the changes work in your deployment environment — that requires running the application and its tests against the target runtime

### 8.11. Transformation & Safety

  * Preserve behavior

  * Avoid breaking changes

  * Validate assumptions

  * Apply incremental updates

    src/utils/DateHelper.java. Convert from
    java.util.Date to java.time.LocalDateTime.

    - Preserve all existing method signatures
    - Do not introduce new features
    - Apply only date-related changes

Modernization must never change system behavior accidentally. Assistants sometimes propose more changes than requested.

You can control this by telling the assistant:

  * "Preserve behavior."

  * "Do not introduce new features."

  * "Apply only these changes…"

  * The phrase "apply only these changes" is your primary safety mechanism — without it, the assistant will opportunistically modernize anything it notices

    or log levels; only the method name.

Assistants are particularly strong at repetitive changes (e.g., replacing patterns across dozens of files). This is one of the best use cases for AI in enterprise systems.

But large changes also magnify risks; every change must be reviewed carefully.

Repetitive multi-file changes are the sweet spot for AI-assisted development. The pattern is simple enough that the assistant gets it right, and the volume is high enough that doing it manually is painful.

  * Run tests

  * Compare old vs. new behavior

Validation is your final safeguard:

  * Run tests

  * Compare old vs. new behavior

  * Ask the assistant for self critique

  * Request explanations for each change

  * Document why the modernization occurred — future developers need that context

  * Self-critique catches a surprising number of issues before you compile, but it is not a substitute for running tests

The earlier modules established what AI coding assistants do, how context flows into them, how configuration shapes their behavior, how MCP extends their reach, and what practical workflows they enable. Here we name the specific surfaces Copilot provides for each of those concepts, with attention to how Copilot’s choices differ from the abstract patterns covered earlier.

### 9.2. Model Selection

Three vendor families surface in the Copilot picker, shared across Chat, Plan mode & Agent Mode.

  * **GPT** : broad-coverage default

  * **Claude** : multi-step reasoning & code

  * **Gemini** : select plans & regions

Pick deliberately by task. The picker is the same surface everywhere, but the families behave differently under load.

Family | Reach for it when…​  
---|---  
**GPT** | Well-rounded default; broad task coverage  
**Claude** | Multi-step reasoning, complex refactors, Plan agent  
**Gemini** | Your plan exposes it and the task profile fits  
  
**Plan tier gates the list:** Pro, Pro+, Business, Enterprise. Enterprise admins can further restrict per organization.

The three families serve broadly overlapping but distinguishable purposes. GPT models are typically the well-rounded default and the one most students reach for first. Claude models are common in workflows that lean on multi-step reasoning, including Plan agent runs and complex refactors. Gemini sits alongside the other two as an option teams reach for selectively. The right discipline is to treat the picker the same way you would treat a model choice in any other AI-assisted tool: pick by what the task needs, not by what feels biggest.

#### 9.2.1. Optimizing Model Choice

Models trade reasoning depth against speed & cost. Match the model’s depth to the task’s load rather than reaching for the biggest option by default.

  * **Reasoning-leaning** : Plan agent, hard refactors

  * **Speed-leaning** : completions, quick Ask turns

  * **Balanced** : general-purpose default

Avoid the "always pick the biggest" reflex. Premium reasoning on a small completion is overhead, not value.

Model optimization is mostly a question of matching the cognitive load of the task to the cognitive depth of the model. A small completion does not need a model that takes ten seconds to think; a multi-file refactor benefits from a model that does. The mistake students make most often is treating reasoning-leaning models as a status symbol rather than a tool. Treating the picker as a deliberate choice every time builds the habit that scales when the team starts paying real money for Copilot use.

#### 9.2.2. The GitHub AI Credits System

Higher-cost usage is metered through **GitHub AI Credits** , billed by token consumption (input, output, cached) at per-model rates, not flat per-request units. Choosing the right model becomes real discipline rather than a slogan.

  * **Metered** : Chat, Plan mode, Agent Mode, code review, CLI, coding agent

  * **Not metered** : inline completions and Next Edit suggestions

  * **Overages** : billed per token in AI Credits (1 credit = $0.01); admins can set budgets and caps

Credit burn is driven by **both** model choice and context size; big models on large codebases spend fastest.

Plan | Credits & controls  
---|---  
**Pro** | Monthly AI Credit allowance  
**Pro+** | Larger allowance, broader picker  
**Business** | Per-seat allowance, org-level controls  
**Enterprise** | Org-level allowances, budgets, policy enforcement  
**Max** | Highest allowance for sustained agentic use  
  
**Hard limit when credits run out** : once the monthly allowance is spent, premium features stop until you buy more credits or the cycle resets. Inline completions keep working. Base subscription prices are unchanged.

GitHub AI Credits serve two roles. For individuals, they surface the cost of choices that would otherwise be invisible; because billing is now per token, a single large-context agentic run can spend a meaningful share of a monthly allowance in one shot. For organizations, credits give administrators a usage signal and a budget control surface. Unlike the previous premium-request system, this is not a soft constraint. When the allowance is exhausted, premium features stop until more credits are purchased or the billing cycle resets; inline completions remain available. Teams should plan for it the way they plan for any other consumption-based developer tool, with budgets set deliberately.

#### 9.2.3. Spending Credits

Billing is per token. Two choices drive the bill: **which model** you pick and **how much context** you send. A few habits keep usage efficient without watching a meter all day.

  * **Free surfaces first** : inline completions and Next Edit suggestions cost nothing; lean on them for routine code

  * **Match the model to the task** : small, fast models for simple work; save premium and large-context models for genuinely hard, multi-step problems

  * **Scope the context** : point Copilot at the files that matter and close irrelevant tabs; fewer tokens in means fewer credits out

  * **Plan before you act** : a wrong Agent run spends credits twice (the bad run, then the redo); catching it in Plan mode costs one prompt

**The cheapest credit is the one you never needed to spend.**

Burns more | Burns less  
---|---  
Biggest model for everything | Model matched to the task  
Whole-repo context | A few relevant files  
Straight to Agent Mode | Plan first, then Agent  
Chat for routine edits | Inline completions (free)  
Long, unattended Agent loops | Tight scope, reviewed early  
  
Because metering moved from flat premium-request units to token consumption, efficiency is now continuous rather than per-request: every extra file of context and every avoidable agentic turn has a marginal cost. The most common source of surprise burn is a long Agent Mode run that iterates on test failures with broad context: exactly the case where a quick Plan-mode pass first would have caught the misunderstanding for one prompt. Treating credits the way you treat any consumption-based developer tool (scope deliberately, monitor usage, set a budget) turns the hard stop from a nasty surprise into a planned constraint.

### 9.3. Copilot Chat Surfaces

Five surfaces, same model, different scope and supervision:

  * **Chat Panel** : multi-turn investigation

  * **Inline Chat** : quick local question

  * **Plan mode** : reviewable plan before execution

  * **Agent Mode** : autonomous execution (now also coordinated multi-file edits)

  * **Agents Window** : multi-project orchestration

Surface | Scope | Behavior | Typical use  
---|---|---|---  
**Chat Panel** | Workspace-wide | Read-only Q&A | Multi-turn investigation  
**Inline Chat** | Selection-local | Read-only Q&A | Quick "what does this do?"  
**Plan mode** | Workspace-wide | Produces a reviewable plan; no edits | Scope a change before Agent runs  
**Agent Mode** | Workspace + tools | Runs & edits | Autonomous execution; coordinated multi-file refactors  
**Agents Window** | Multi-project, dedicated window | Runs agent sessions | Cross-project agent orchestration  
  
The Chat-family surfaces serve different needs in the engineering day. The panel is the workhorse for multi-turn investigation across a workspace. Inline Chat is the ephemeral, locally-scoped question that does not need to be remembered. Agent Mode handles both autonomous execution and coordinated multi-file edits; the model reads, runs commands, and proposes diffs, with Agent Logs and diff review as the supervision surfaces. Engineers who pick the right surface for each moment get more from Copilot than engineers who default to whatever Chat opened first.

#### 9.3.1. Chat Panel

Sidebar conversation in VS Code or on GitHub.com. Persistent within a session and workspace-aware when scoped explicitly.

  * **Persistent** across turns in the session

  * **Workspace-aware** via `#codebase`

  * **Chat participants** : `@terminal`, `@vscode`, `@github`

  * **Slash commands** : `/explain`, `/fix`, `/tests`, `/doc`, `/new`

Best for multi-file questions and multi-turn investigation.

The Chat panel is where most of Copilot’s conversational capability shows up. Engineers who treat it as a search box leave value on the table; engineers who treat it as a working conversation (with attached context, follow-up turns, and explicit scoping via participants and slash commands) get answers that compound. Conversation history is the mechanic that makes this possible: the panel remembers what was already established so the next turn can build on it without restating the situation.

#### 9.3.2. Inline Chat

Floating prompt anchored to your selection, reached with `Ctrl`+`I` / `Cmd`+`I`.

  * **Anchored** to selection & surrounding code

  * **Ephemeral** : no history across invocations

  * **Quick turns** : "what does this do?", small edits

Best for local questions you act on once. The panel remembers; Inline Chat does not.

Inline Chat exists because there is a class of question ("what does this block do," "rename this in place," "tighten this assertion") that does not deserve the overhead of opening the panel and attaching context. The price for that ergonomic shortcut is that Inline Chat has no memory. Use it for questions whose answer you will read and act on once. Use the panel for questions whose answer you will refer back to or build on.

#### 9.3.3. Plan mode

A planning surface that builds a reviewable implementation plan before any code is written. Enter it from the chat mode dropdown or with `Shift`+`Tab`.

  * **Workflow** : describe the goal, answer clarifying questions, review the plan, approve

  * **Plan artifact** : the Plan agent writes the plan to a markdown file (`plan.md` in session memory; custom planning agents can persist `*.plan.md` in the workspace)

  * **No edits** : Plan mode produces a plan, not a diff

  * **Handoff** : "Start implementation" passes the approved plan to Agent Mode

**Edit mode (Copilot Edits) is deprecated** : its multi-file editing role moved into Agent Mode. Treat Plan mode → Agent Mode as the path forward.

Plan mode addresses the failure pattern where an agent starts editing before it understands the task. Instead of producing a diff, it analyzes the request, asks clarifying questions, and emits a structured plan the engineer reviews and approves, written out as a markdown plan file so it can be read, edited, and handed off. From there, "Start implementation" transfers the approved plan to Agent Mode, which does the actual editing under the usual Agent Logs and diff-review supervision. The deprecated Copilot Edits surface previously filled the multi-file coordinated-edit gap; that role now belongs to Agent Mode, and Plan mode sits in front of it as the deliberate scoping step.

#### 9.3.4. Agent Mode

Copilot operating autonomously in the IDE. The contract is simple (goal in, diff out), but the supervision discipline is non-negotiable.

  * **Workspace actions** : reads files, runs terminal commands, proposes diffs

  * **Agent Logs** : your supervision surface

  * **Diff review** : Copilot proposes; you approve

  * **Pair with Plan agent** : approve a plan before the run

  * **Coordinated edits** : also handles the multi-file changes Copilot Edits used to

Agent Mode is the surface where the supervision discipline from earlier in the course earns its keep. The model can read your whole workspace, run terminal commands, and edit files; the only thing between an agent run and your codebase is your review of the Agent Logs and the proposed diff. Students who skip those steps will produce green test suites that hide broken code; students who treat them as gates will catch the cases where the agent took a wrong turn. The Copilot Interaction Modes chapter covered the mode itself; this slide is your reminder that the same discipline applies whenever Agent Mode is in the picker.

#### 9.3.5. Agents Window

A dedicated VS Code window for agent-first, multi-project work.

  * **Sessions** : agent sessions across workspaces, grouped by project

  * **Customizations** : custom agents, skills, instructions, hooks, MCP servers & plugins

  * **Chat** : center conversation & prompts

  * **Changes** : Files & Changes tabs with diffs

  * **Session controls** : New, New Sub-Session, Tasks, Add Feedback

  * **Diff actions** : Commit, Merge, Checkout, Discard

Best for cross-project agent orchestration: many sessions, one supervisor.

The Agents window is VS Code’s purpose-built home for working with Copilot agents across more than one project at a time. Where Agent Mode lives inside the regular Chat panel and runs against the active workspace, the Agents window is its own dedicated window. Four areas make up the surface: a sessions list on the left grouped by project; a customizations panel surfacing custom agents, skills, instructions, hooks, MCP servers, and plugins; a chat area in the center; and a Changes panel on the right whose Files & Changes tabs let an engineer commit, merge, checkout, or discard the agent’s work. Sub-sessions and Tasks let a single supervisor fan work out across projects; the **Open in Agents** button is the entry point from any running Chat session. The two flanking panels are shown in isolation below.

### 9.4. The Copilot Coding Agent

The Copilot coding agent lives in GitHub rather than the IDE. It is the surface for asynchronous, sandboxed work whose result the team will review as a PR.

  * **Asynchronous** : returns a draft PR

  * **Sandboxed** : Actions runner, branch protections, approval gates

  * **Initiated** by assigning an issue or prompting on GitHub.com

  * **Mission Control** : parallel agent tasks

The structural sandboxing is what makes useful autonomy safe without granting keys to production.

The Copilot coding agent is the surface that brings the agent experience to GitHub-native, asynchronous work. It is appropriate for tasks whose acceptance criteria are clear enough that an engineer can review the result as a PR rather than as a stream of decisions during the work itself. The structural sandboxing (branch protections, controlled network access, approval gates before CI/CD) is what makes it safe to grant the agent useful autonomy without granting it the keys to production.

#### 9.4.1. The Execution Loop

The agent’s loop is the safety envelope. Every run goes through the same sequence, and self-review plus security scanning are not optional steps.

  * **Research** : read the repository

  * **Plan** : outline the implementation

  * **Commit** : push to a draft PR

  * **Self-review** : run Copilot code review on the diff

  * **Security scan** : built-in scanning before request

  * **Request review** : hand off to a human

Merge is never automatic; the final step is always a human review.

The execution loop is deliberately structured so that humans see the work as a PR (a familiar review artifact) rather than as a stream of edits. Self-review and security scanning catch the most common issues before the work is offered for human review. The result is that the human review step receives work that has already cleared two automated quality gates, which makes the review more focused on judgment and less on catching the obvious mistakes.

#### 9.4.2. Supervision

Supervision surfaces mirror IDE Agent Mode, but with different visibility because no engineer is watching during the run.

  * **Session logs** : cloud-side Agent Logs

  * **PR review comments** : in-loop feedback channel

  * **Branch protections** : by design; CI/CD needs human approval

  * **Model picker** : Agents panel, by task complexity

Structural gates rather than operator-dependent ones; the safety envelope holds even when "the operator forgot" is the failure mode.

The supervision model for the coding agent is built around the assumption that no engineer is watching during the run. Session logs preserve the full reasoning trail so review can happen after the fact. PR review comments are the channel that lets a reviewer course-correct the agent the same way they would course-correct a teammate. The structural gates (branch protections, controlled internet access, approval before CI/CD) are not features the operator opts into; they are part of how the surface is built. That distinction matters in environments where "the operator forgot" is not an acceptable failure mode.

### 9.5. Copilot Spaces

Curated, named context collections. Reference a Space to load its bundle into Chat or Agent Mode.

  * **Files and references** : code, docs, specs

  * **Instructions** : Space-specific guidance

  * **Named and shareable** : travels with the team

  * **Cumulative** : loaded **on top of** the mode’s normal context

Spaces solve a recurring practical problem: the same handful of files, references, and conventions need to be in front of Copilot every time a particular kind of work happens. Without Spaces, that bundle gets reassembled by hand each time, with predictable drift across the team. With Spaces, the bundle is named, version-managed where appropriate, and reusable across the team. The Space is the team’s persistent shared context; it complements `copilot-instructions.md`, which sets always-true rules, by providing on-demand grounding for specific kinds of work.

#### 9.5.1. When to Use

Spaces, prompt files, and configuration files all let teams encode reusable inputs to Copilot. They solve different problems.

Surface | What it encodes  
---|---  
**Copilot Space** | A reusable **context bundle** : the files, references, and ad-hoc instructions a kind of work needs in front of Copilot. Loaded when you reference the Space.  
**Prompt file** (`.github/prompts/NAME.prompt.md`) | A reusable **prompt** : what to ask Copilot in a specific situation. Invoked as a slash command.  
**`copilot-instructions.md`** | **Always-true rules** for the repository. Loaded on every Copilot turn in that repo.  
**Path-specific instructions** | Rules scoped to a directory or language via `applyTo` globs.  
  
The discipline: ask "is this _what I want considered_ , _what I want asked_ , or _what should always be true_?" The right surface follows.

The four configuration surfaces work together rather than competing. `copilot-instructions.md` and path-specific instructions encode standing rules: the things that should always shape Copilot’s behavior. Prompt files encode reusable asks, the specific prompts a team finds itself writing repeatedly. Spaces encode reusable context, the files and references that should be in front of Copilot when a particular kind of work happens. Most production Copilot setups use all four together, layered so the engineer’s role is to pick the work, not to assemble the context.

### 9.6. Copilot Extensions

Third-party chat participants registered via GitHub Apps. Appear as `@extension-name` in Chat.

  * **Examples** : `@azure`, `@docker`, `@sentry`, `@stripe`

  * **GitHub App** : installed at org or account level

  * **Chat context access** when invoked

  * **Marketplace** : discoverable in the GitHub Marketplace

Extensions are the answer for organizations that want Copilot to speak about systems that live outside the repository. Without Extensions, every cross-system question requires the engineer to context-switch into the other tool. With Extensions, the question is asked in Chat and the Extension brings the answer back. Each Extension is a third-party integration with access to Chat context. Review it the same way you would review any other SaaS integration.

#### 9.6.1. Trust Model

Treat Extensions like any third-party OAuth application.

  * **Review scopes** at installation

  * **Audit usage** on a cadence

  * **Remove** what you do not use

  * **Org-level controls** restrict what can be installed

Chat-context access is equivalent to a SaaS integration seeing what you paste.

The trust model for Extensions is identical to the trust model for any GitHub App or third-party OAuth integration. The difference is that the access path is conversational rather than API-driven; an Extension that is `@`-mentioned in Chat sees the conversation context, including any code or data that has been pasted in. For most teams, the right discipline is a periodic inventory: which Extensions are installed, who installed them, when were they last used, and is the trust review still current. Extensions that have not been used in months are not free; they are still part of the trust footprint.

#### 9.6.2. Plugins, Extensions & Custom Agents

The Copilot surface uses three similar-sounding concepts for different things. Untangling them prevents a recurring student confusion.

Concept | What it is  
---|---  
**Copilot Extensions** | Third-party chat participants registered via **GitHub Apps**. Live in the GitHub Marketplace. Cross-organization. Example: `@azure`.  
**Copilot CLI plugins** | Installable packages that bundle MCP servers, agents, skills, and hooks for **Copilot CLI**. Local terminal tooling. Installed from GitHub repositories.  
**Custom agents** | Specialized **agent configurations** defined in `.agent.md` files. Scoped to a repository. Author by hand or via the Copilot CLI `/agent create` wizard.  
  
The three live in different places, distribute differently, and carry different trust models. Read the documentation carefully when you encounter the words in the wild.

The terminology overlap is unfortunate but real. The shortest mental model: Extensions reach outside the team; plugins reach inside the terminal; custom agents reach inside the repository. The trust models follow from the reach: Extensions need vendor-style review because they are third-party services; plugins need code review because they ship with executable tooling; custom agents are part of the codebase and reviewed like any other configuration file.

### 9.7. Workspace Indexing

Copilot’s cross-file retrieval quality depends on which index mode is active. Three modes exist, with substantially different performance characteristics.

Mode | What it is  
---|---  
**Remote index** | Server-side index of the repository, maintained by GitHub. Fastest and most complete. The production-quality experience.  
**Local index** | Built and held on the engineer’s machine. Used when remote indexing is unavailable or disabled. Less complete; performance depends on local resources.  
**Basic index** | Lightweight, in-IDE retrieval over open and recently edited files. Sufficient for small workspaces; degrades quickly as the repository grows.  
  
The active mode is determined by organization policy and platform configuration; engineers do not choose it per turn.

Workspace indexing is the invisible plumbing behind `#codebase`. Engineers do not configure it directly each time they invoke Chat; the active mode is set by organization policy. Understanding the three modes matters because they explain why two engineers running the same `#codebase` query against the same repository can get different-quality results; they may be running against different index modes without realizing it. The standard production setup is remote indexing; teams investing in Copilot at scale should treat enabling it as a prerequisite, not an optimization.

#### 9.7.1. Practical Implications

Index quality shapes every workspace-scoped Copilot interaction.

  * **`#codebase` quality** follows the active index

  * **Cross-file refactoring** relies on the index to find call sites

  * **Enterprise enablement** : admin-controlled, often a data-residency conversation

  * **Data residency** : remote indexing means GitHub holds the index

The practical implication of the indexing modes is that the rest of the Copilot story assumes remote indexing. Students who experience the course on local or basic indexing will see degraded versions of features that work well in the documentation and the labs. For teams adopting Copilot at scale, the right sequence is: confirm data-residency requirements, enable remote indexing, then exercise the workspace-scoped features against a repository the team actually works in. Doing this before broad rollout prevents the "Copilot didn’t see my file" frustration that erodes confidence in the tool.

### 9.8. Copilot Configuration

`copilot-instructions.md` is the repository-level config. Copilot’s entry into the Module 3 instructions hierarchy.

  * **Location** : `.github/copilot-instructions.md`

  * **Always loaded** : every Copilot turn in the repo

  * **Contents** : conventions, stack, style, hard boundaries

  * **Living documentation** : update when conventions change

Where the Configuration Standards module taught the concept of an instructions hierarchy as a cross-tool pattern, this slide grounds it in the Copilot-specific name and file location. CLAUDE.md is the canonical name for behavioral configuration in the Claude family; `copilot-instructions.md` is the Copilot equivalent: same role, different name, same discipline of treating the file as code. Most teams adopting Copilot author the file early and then update it whenever a convention change would otherwise have to be remembered by every engineer.

#### 9.8.1. Path-Specific Instructions & `AGENTS.md`

Repository-wide instructions are the default. Two additional surfaces let teams scope rules more precisely.

  * **Path-specific instructions** : `.github/instructions/*.instructions.md` files with an `applyTo` glob in the front matter. Apply only when Copilot is working on files matching the glob.

  * **`AGENTS.md`** : agent-specific behavioral guidance. Apply when Copilot is operating in agent mode (IDE Agent Mode or the coding agent). Use for rules that only make sense for autonomous work.

    
    
    ---
    applyTo: "tests/**/*.py"
    ---
    - Use pytest fixtures rather than setUp/tearDown
    - Prefer parameterized tests for input variations
    - Mark slow tests with @pytest.mark.slow

Path-specific instructions let the team scope rules to where they apply. A repository with both Python and TypeScript probably wants different test conventions for each, and those rules belong in path-scoped files rather than in the repository-wide instructions where they would either bloat the file or fail to apply. `AGENTS.md` is the parallel mechanism for agent-only rules: guidance that only makes sense when Copilot is operating autonomously. Together with `copilot-instructions.md`, these three surfaces cover the standing-rule surface area of the configuration hierarchy.

### 9.9. GitHub Platform Integration

Four GitHub-native features extend Copilot into the team’s review and triage workflow:

  * **Copilot code review** : inline suggestions on PR diffs

  * **Auto-generated PR summaries** : a starting draft from the diff

  * **`@github` Chat participant**: queries against GitHub state

  * **Assigning issues to Copilot** : hand well-scoped work to the coding agent

The IDE-side features make individuals more productive. The GitHub-side features change how the team operates around code.

Where the IDE-side features make individual engineers more productive, the GitHub-side features change how the team operates around code. Copilot code review and PR summaries change the quality of PR conversations; the `@github` participant lets Chat speak about remote state; assigning issues to Copilot moves the coding agent into the team’s normal queue of work. Teams that adopt these features find that Copilot stops being a tool you reach for and starts being part of the platform. Review comments arrive from it the same way they arrive from teammates, and the criteria for sending work its way becomes part of the team’s normal triage discussion.

#### 9.9.1. Code Review on Pull Requests

Inline review suggestions on PR diffs. Runs automatically on coding-agent PRs.

  * **Request on demand** from the PR UI

  * **Inline suggestions** anchored to specific lines

  * **Self-review** runs automatically on coding-agent PRs

  * **First pass, not final gate** : human review still decides

Copilot code review brings the assistant into the team’s normal review workflow. The mechanism is intentional: review comments appear inline on the diff, anchored to specific lines, in the same UI a human reviewer would use. Teams adopting the feature typically pair it with a clear convention about which review comments are advisory and which are blocking. As with any automated review tool, the value is in the comments that catch something a human would have missed, not in the comments that restate what was obvious.

#### 9.9.2. PR Summaries & the `@github` Participant

Two features that complete the GitHub-side integration.

  * **PR summaries** : auto-generated from the diff; a starting draft

  * **`@github` participant**: Chat queries against GitHub state

  * **Requires GitHub authentication**

  * **Use cases** : "what changed here," "discussion on issue #42," "agent’s PRs this week"

The combination of PR summaries and the `@github` participant changes the surface area of what Copilot can help with. Engineers who treat PRs as a primary work artifact find that Copilot’s awareness of PR state (content, discussion, history) makes Chat more useful for review prep, status updates, and cross-PR queries. The dependency on GitHub authentication is a small ergonomic cost; the upside is that the participant can speak about state the engineer would otherwise have to navigate to manually.

#### 9.9.3. Assigning Issues to Copilot

The clearest use case for the Copilot coding agent is assigning a GitHub issue to Copilot. The trick is knowing which issues to assign.

A useful test before assigning: "If a junior engineer brought back this PR tomorrow, could I review it as a PR or would I need to pair on the design?" If the answer is "review as a PR," it is a candidate.

**Good fits:** well-scoped, lower-risk tasks with clear acceptance criteria; work where the path is known but the edits are numerous; tasks you would be comfortable reviewing as a PR without pairing.

**Poor fits:** open-ended architectural decisions; work that requires interactive debugging or operator intuition; tasks where the acceptance criteria are still being negotiated.

The assigning-to-Copilot decision is the same decision a team makes whenever it delegates work: what is the cost of a wrong answer, how reversible is it, and how clear is the spec. Issues that pass the test become predictable wins; issues that fail the test become PRs that the team will spend more time correcting than it would have spent doing the work directly. Teams that adopt the coding agent successfully usually invest in the issue-writing discipline before they invest in the agent itself.

### 9.10. Copilot CLI in CI/CD Pipelines

**Copilot CLI** brings the agent into the terminal. In non-interactive mode (`copilot -p`), it becomes a **CI/CD primitive** : a pipe you can drop into a GitHub Actions workflow.

  * **Interactive mode** : terminal-native agent; same model as IDE Agent Mode, different ergonomics

  * **Non-interactive mode (`copilot -p`)**: stdin carries shell evidence, stdout carries analysis

  * **Composable** : the same role `grep`, `jq`, or `pytest` plays in a pipeline

  * **No human in the loop** : the plumbing is easy; output reliability and safety are the work

Copilot CLI completes Copilot’s coverage of the developer’s day. Engineers who work primarily in the terminal (Linux administrators, SREs, build engineers) have the same need for an AI coding assistant as IDE users, with terminal-native ergonomics. The non-interactive `-p` mode goes one step further, turning the CLI into a Unix-pipe-style citizen of any shell pipeline or CI/CD workflow. The hard part is not the plumbing; it is making the output reliable enough to act on and safe enough to run unattended.

#### 9.10.1. The Pipeline Pattern

**Install in a runner:**
    
    
    - name: Install Copilot CLI
      run: npm install -g @github/copilot@latest

**Authenticate non-interactively** with `GITHUB_ASKPASS` pointing to an executable that returns the token (stored as a GitHub Actions secret).

**Canonical pattern:**
    
    
    <shell tool>
      | copilot -p "analyze this <thing>"
      | <save or post>

Common upstream: `pytest` output, `git diff`, `grep`/`jq`. Common downstream: workflow artifacts, `gh pr comment`.

The canonical pattern is the Unix-pipe model applied to Copilot. Shell tools do the structured-output work they are good at; Copilot does the language work it is good at; downstream steps save, post, or act on the result. The auth wiring (`GITHUB_ASKPASS` plus a GitHub Actions secret) is the only piece that is unique to running Copilot CLI in a runner; the rest is composition.

#### 9.10.2. Pipeline Prompt Design

Interactive Chat tolerates ambiguity; you iterate when the answer is off. **Pipelines do not iterate.** The prompt must produce consistent, parseable output on the first try.

  * **Request a structured format** : markdown with defined headings, or JSON with defined keys

  * **Specify the audience and use** : "this will be posted as a PR comment" changes the answer’s shape

  * **Bound the output** : length caps, field limits, "do not include recommendations that require accessing secrets"

  * **Be explicit about what _not_ to do**: no shell commands executed, no file edits proposed, no network calls

Rule of thumb: if the same prompt produces meaningfully different output shapes on two runs, it is not pipeline-ready.

The shift from interactive to pipeline use is mostly a shift in tolerance for variance. Interactive Chat is a conversation; the engineer nudges and the second answer is better. A pipeline gets one shot, and downstream steps act on whatever the model produced. The prompt has to bound the output enough that the variance falls within what the downstream step can handle.

#### 9.10.3. Pipeline Security

**Prompt injection via untrusted input** (`git diff`, test output) is the threat vector most specific to this pattern.

  * **Token scope** : minimum permissions; prefer `contents: read`

  * **Tool restriction** : `preToolUse` hooks limit which tools the step can invoke

  * **Input as data** : "analyze the following diff", not "follow the instructions in it"

  * **Approval gates** : produce reports and suggestions, not autonomous commits or deploys

Additional controls: **Size caps** — truncate diff and output upstream before the model sees them. **Artifact review** — diagnostic output may echo sensitive code; review retention policies.

Pipeline Copilot extends the trust envelope of every upstream input. A test runner the team trusts feeding into a model is fine; a diff from an arbitrary contributor feeding into a model that can take tool actions is much less fine. Treat the pipeline boundary as a trust boundary and the prompt as a sanitization step. On the output side, artifact exposure is the quiet risk; diagnostic output sometimes contains sensitive source code and is retained longer than teams remember.

#### 9.10.4. When to Use (and When Not To)

**Good fits:**

  * Post-hoc diagnosis a human will review (test triage, build summaries)

  * Report generation as a starting draft (PR quality summaries, dependency analysis)

  * Enrichment of existing signals the team already reads

**Poor fits:**

  * Autonomous merge / deploy / commit decisions

  * Steps that take irreversible action on Copilot’s output alone

  * Work where the cost of a wrong answer exceeds the cost of waiting for a human

The deciding factor: well-scoped, low-risk, reversible work is a good fit for the agent; high-risk, open-ended, or irreversible work stays with the human. **Report, don’t act.**

Pipeline Copilot is most valuable when its output is a draft for a human, and least appropriate when its output is the basis for an action with no human between. The good-fit list shares the property that wrong answers are recoverable; the poor-fit list shares the property that wrong answers compound or cannot be reversed. Locate the right human approval gate by asking what the worst-case outcome looks like if the step produced bad output and the next step acted on it without supervision.
