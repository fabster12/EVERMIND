# AI-Native FDE Capstone using Google ADK

## AI-Native FDE Capstone: Build an Agentic System with Google ADK

Lab 1

  * Define an agentic project and write a description and plan that you get approved before building
  * Build a working agent in Google ADK, escalating from one agent to tools, state, workflows, or a team only as the problem demands
  * Apply greenfield or brownfield constraints, treating any existing system as a black box
  * Prove your agent behaves with at least one evaluation set or test suite
  * Conduct a code review and a Go/No-Go decision before you ship
  * Present your build and your design decisions in a timed showcase, and deliver your deck and a working repository to graduate

### 1.1. The Brief

**Do something agentic.** Build an AI agent in Google ADK that takes a real task off a real person’s plate.

You choose the problem. You write the plan. You build, evaluate, and present the agent. The capstone has one purpose: to show that you can develop agentic AI in a Google ADK environment, end to end, on a problem nobody scripted for you.

### 1.2. Success Criteria

Read these before you pick a problem. They define what "done" means, and you’ll agree to them with your instructor at the approval gate.

# | Criterion  
---|---  
1 | The agent is built in Google ADK and runs from a clean checkout  
2 | It’s genuinely agentic: it decides and acts through tools, state, or sub-agents, not a single prompt and response (calls at least one tool, reads from or writes to session state, or delegates to a sub-agent; a prompt returning free text with no tool call or state access does not qualify)  
3 | It started from a written description and plan, approved before any agent code was written  
4 | Its output is constrained by a Pydantic `output_schema` and validated, not free text  
5 | At least one evaluation set or test suite shows the agent behaves as you claim, including one failure path  
6 | You present the build and explain the decisions and trade-offs behind it  
7 | On presentation day, your group delivers a completed presentation deck and a working, runnable zip of the repository  
  
If your project is brownfield, add criterion 8:

# | Criterion  
---|---  
8 | The existing system is unchanged. Your integration calls it as a black box and transforms its output only after receiving it.  
  
### 1.3. How the Capstone Runs

The work moves through four phases. Phase 1 gates the other three: you don’t start building until your plan is approved.

The phases map onto the capstone sessions. Your instructor sets the exact schedule; a common shape is one session to plan and get approved, two to build, and one to prove it works and present.

Phase | You produce | Gate  
---|---|---  
1: Define and Plan | A project description and plan | Instructor approval  
2: Build in ADK | A running agent with structured output | Self-check against criteria 1 to 4  
3: Prove It Works | An eval set or test suite, then a code review | Self-check against criterion 5; code review passes  
4: Showcase | A five-minute presentation, a deck, and a working repo zip | The Go/No-Go decision; deck and zip delivered by 9:00 AM  
  
### 1.4. Phase 1: Define Your Project and Get It Approved

#### 1.4.1. Step 1: Pick a Problem

Find a task that’s repetitive, rule-bound, and ends in a decision or a structured result. Good agentic problems read input, apply judgment, and produce something a person or system can act on.

If a single model call would solve your idea, it’s too weak for the capstone. If your idea is "summarize this text" or "answer this question," push further: ask what the agent should **do** with the answer.

#### 1.4.2. Step 2: Choose Greenfield or Brownfield

  * **Greenfield.** You build everything. No existing system constrains you.

  * **Brownfield.** You integrate with a system that already exists and that you can’t change. Read _Brownfield Rules_ below before you commit.

Either path can meet every success criterion. Pick the one that fits your problem.

Greenfield | Brownfield  
---|---  
You own the full agent design | You wrap an existing system  
Constraint: scope creep — keep the problem bounded | Constraint: boundary — you do not modify what’s inside the wrapper  
Common pitfall: building a demo, not an agent | Common pitfall: trying to modify the black box output directly  
Working when: the agent calls a tool and produces structured output end-to-end | Working when: the wrapper returns clean data and the agent acts on it  
  
#### 1.4.3. Step 3: Write the Description and Plan

Write a short document, one to two pages. This format answers four questions:

  1. **Problem.** What task are you automating, and who feels the pain today?

  2. **Solution.** What will the agent do? Name the inputs, the output shape, and the decisions it makes.

  3. **Scope.** What’s in, and what’s explicitly out? For brownfield, name the existing system and state that you won’t change it.

  4. **Risks.** Where could the agent be wrong, and what’s your guard against it?

Add a build sketch: the ADK constructs you expect to use and why. Keep it honest about size. A document that promises a five-agent system you can’t build in the time is worse than one that scopes a single agent well.

__Tip

You can run OpenSpec on your capstone if you want the artifacts in a format you already know: `openspec init`, then propose the change. The plan is what matters, not the tool you write it in.

#### 1.4.4. Step 4: Present Your Design for Sign-Off

On the first day of the capstone, present your design to your instructor. Acting as your architect, they review and sign off on the design before you build, the way an architect or an operations lead would on a real project, checking that:

  * The scope matches the problem and fits the time

  * The output shape is concrete enough to validate

  * The risks are real and have guards

  * For brownfield, the black-box boundary is clear

You work mainly as a developer, but you own the design and carry some deployment responsibility, so your instructor also probes the architectural considerations below. You get a sign-off or a redirect. Don’t write agent code until you have the sign-off.

#### 1.4.5. Architectural Considerations

Once you have an initial design, your instructor probes how it attends to the qualities a production system has to meet, the non-functional requirements (NFRs) drawn from the well-architected cloud pillars. Come to the review ready to answer for each.

Concern | What your instructor asks  
---|---  
**Security** | How does your agent get its permissions for what it can and can’t do? How do you prevent it from getting unnecessary tool access? How do you prevent it from getting unauthorized network access?  
**Reliability** | When a tool call or the model fails, how does the agent degrade instead of crashing? How will you know whether it’s giving valuable responses in production, rather than inappropriate ones? How does the design hold up, and how will you scale the agents when load hits?  
**Performance efficiency** | How do you identify the slowest part of the agent (the tool chain, the harness, tool calls, I/O), and how would you measure it? What performance trade-offs did you make? How does latency hold up as load grows?  
**Cost effectiveness** | What drives the cost of running your agent? Where is spend going to undifferentiated work you could make deterministic instead of giving to the model? How would you evaluate models over time and right-size the model and infrastructure to the actual workload?  
**Operational excellence** | What do you need to monitor to know the agent is doing its job properly? How will you track both quantitative metrics and qualitative results? Do you have a runbook for recovery when it breaks? Is the whole environment recreatable from code?  
**Deployment** | How would you deploy this: managed services, or roll your own? (Google Cloud Platform is FedEx’s primary target.) What compute model fits: a container, a virtual machine, or serverless? How does it scale in that target, and where do your data sources go?  
  
Not every cohort deploys to a live environment, so treat the deployment questions as design questions: be ready to explain how you’d deploy, even if you don’t.

__Note

Before starting Phase 2, read the rules section for your project type: **Greenfield Rules** if you are building from scratch, or **Brownfield Rules** if you are integrating with an existing system.

### 1.5. Greenfield Rules

You own the whole system. Your only constraints are your plan and the success criteria. Use the time you save on integration to make the agent’s behavior provable: a clean output schema, a real eval set, a tested failure path.

### 1.6. Brownfield Rules

A brownfield project integrates with a system that already exists. Treat that system as a **black box**.

Rule | What it means  
---|---  
Don’t change the internals | You may not edit the existing system’s code or logic. If you find a bug in it, note it in your write-up. Don’t fix it inline.  
Don’t change the output | The black box returns what it returns. You can’t make it produce a different shape or different values.  
Mocking is allowed | You may stand in a fake that returns the same shape of output, so you can develop and test without the real system. Use a mock only when the real system requires credentials, a network connection, or is slow to respond; if it is a local module you can call directly, call it.  
Transform after receiving | Once your agent has the output in hand, you can reshape it, enrich it, validate it, and flag problems in it. That transformation is your work, downstream of the black box.  
  
#### 1.6.1. Make the Boundary Explicit

Write a one-page contract that describes only the existing system: what you call, what it returns, and its quirks. End it with a section titled **What This Agent Does Not Touch** , naming the black box as inherited. That contract is the line between what you own and what you inherited.

#### 1.6.2. Enforce the Boundary in Code

Don’t leave the rule in prose alone. Route every call to the existing system through a single tool wrapper, so the seam is visible in the code.

Then prove the boundary held:

  1. Capture the black box’s raw output for a set of sample inputs and freeze it as a baseline, committed alongside your tests.

  2. After you build, run the same inputs and assert the raw output still matches that frozen baseline.

Any difference is a regression, and a regression means you changed something you shouldn’t have.

### 1.7. Phase 2: Build Your Agent in ADK

Start with the simplest thing that could work, then escalate. This is architectural escalation: add a tool, a workflow, or another agent only when the problem demands it, not because it’s available.

__Note

**Brownfield projects:** before writing any wrapper code, run your black-box system on your sample inputs and freeze the raw output as a test baseline. Commit that baseline alongside your tests. See _Brownfield Rules_ , under **Enforce the Boundary in Code** , for the full requirement. Sample B demonstrates this with `EXPECTED_RAW` in `tests/test_pricing_quote.py`.

Work through Phase 2 in this order:

  1. Start with one `LlmAgent` that returns a valid `output_schema`. Get it producing structured output before adding anything else.

  2. Add a tool only when your problem requires it. If your agent needs to look something up or call an external system, add the function tool. Otherwise, skip it.

  3. Verify behavior in `adk web` before writing tests. The Dev UI shows tool calls and final output in real time, so you can confirm the agent is routing correctly before committing to a test suite.

The escalation table below lists the full toolkit in order from simplest to most powerful.

When your problem…​ | Reach for | ADK construct  
---|---|---  
needs one validated answer | a single agent with typed output | `LlmAgent` \+ Pydantic `output_schema`  
needs to look up or change data | a tool | a function tool (typed function returning a status dict)  
needs an external system or service | a tool over that system | `McpToolset` (with `StdioConnectionParams` for local servers), or a function-tool wrapper  
must remember within a run | session state | state keys with `temp:` / `user:` / `app:` scope  
must remember across runs | memory | a memory service + the `load_memory` tool  
runs genuinely separate steps, in sequence or with routing | a workflow graph | an ADK `Workflow` graph (`START`/`edges`, with `FunctionNode`/`JoinNode` for routing and joins)  
splits into specialist roles | a team | a coordinator `LlmAgent` with `sub_agents`, or `AgentTool`  
needs a guard on input or output | a callback or plugin | `before_/after_` callbacks, or a `BasePlugin`  
  
__Note

**One`LlmAgent` can call tools and emit an `output_schema` at the same time.** In ADK 2.x the agent runs its tools during its reasoning and enforces the schema on its final answer, so a single agent both acts and returns a typed result. (ADK 1.x couldn’t do this and forced you to split the work across two agents joined by a `SequentialAgent`.) Reach for a workflow only when you have genuinely separate steps, not to work around a limit that’s gone. Both samples below are single agents.

__Note

An agent that combines tools with `output_schema` prints `UserWarning: [EXPERIMENTAL] feature FeatureName.JSON_SCHEMA_FOR_FUNC_DECL is enabled` when it starts. The warning is expected and harmless; the agent runs normally.

Work top-down. Get a single `LlmAgent` returning a valid `output_schema` before you add a tool, and get one tool working before you add a workflow, so each step leaves you with something that runs.

__Note

The Dev UI (`adk web`) is the fastest way to watch your agent’s tool calls and final output while you build. Use it to confirm behavior before you write tests.

### 1.8. Phase 3: Prove It Works

A demo that works once isn’t evidence. Show that your agent behaves across the cases you care about, including at least one where it should fail gracefully.

Pick at least one of these. Both is better.

  * **An evaluation set.** Capture cases in the `adk web` Eval tab to a `.evalset.json`, set criteria and thresholds in `test_config.json` (`tool_trajectory_avg_score`, `response_match_score`), and run with `adk eval` or `AgentEvaluator` in pytest.

  * **A test suite.** Test the deterministic parts directly, the way the sample solutions do: call each tool function and assert on its return value, including the error path, and construct your Pydantic `output_schema` to prove its validators reject bad values. These tests run without an API key. Keep `InMemoryRunner` for integration-style runs against the live model.

A failure path is any input your agent should handle but doesn’t yet: a missing order ID, an unrecognized category, or a null price. Run that input, document what the agent returns, and confirm the behavior is correct. Fix it if it isn’t.

Cover the main path, at least one edge case, and one failure. If your agent calls a tool that can fail, prove it doesn’t crash when the tool does.

For brownfield projects, include the regression check from _Brownfield Rules_ : the existing system’s raw output is unchanged by your integration.

Phase 3 is complete when you have at least one passing test suite or a green `adk eval` run, with at least one failure path confirmed and documented.

### 1.9. Code Review (RAPID ITC.009)

Before a Meridian agent ships, a second set of eyes signs off on the code. You run that review with your AI coding assistant: point it at your changes and have it report what it finds. This step is FedEx RAPID (the FedEx control framework) control **ITC.009 (Code Review)**.

Each sample carries a `rapid-peer-review` skill in `.github/skills/` that runs the review and writes findings to `docs/rapid-peer-review.md`. If you built your own project, run the same review by hand against these four criteria:

Criterion | What the reviewer checks  
---|---  
**Modified-file inventory** | Every changed file is accounted for, and nothing landed outside the project structure without reason.  
**Secrets and InfoSec** | No hardcoded keys or tokens, no `.env` staged, and no sensitive data in logs or output.  
**Architecture alignment** | The code follows the project’s conventions: data access in one place, tools and agent logic where they belong, type hints and docstrings present.  
**Behavioral scope** | The agent’s output stays inside its schema, tool errors are reported rather than swallowed, and (brownfield) the black box is untouched.  
  
Each criterion gets a rating of **Pass** , **Needs Attention** , or **Fail** , and the review ends with one recommendation: **Pass** , **Conditional Pass** , or **Fail**. Resolve every Fail before the Go/No-Go decision.

Each group presents for five minutes. Use a timer. Structure it however fits your project, covering:

Time | Content  
---|---

~1 min | One design decision and why you made it, in ADK terms  
~1 min | Your evidence: the eval set or test suite, plus your code-review findings  
~1 min | For brownfield, what you did not touch and how you know

**Graduation requirement.** To present and graduate, your group delivers two artifacts to the instructors by 9:00 AM on presentation day:

  1. Your completed presentation deck.

  2. A working zip of your repository that the instructors can unzip and run.

### 1.11. The Go/No-Go Decision (RAPID ITC.004)

Close with a Go/No-Go decision, FedEx RAPID control **ITC.004 (Go/No-Go Decision Gate)**. State whether the build is ready to ship, citing the evidence behind the call:

  * your acceptance criteria, met or not

  * your code-review findings, with every Fail resolved

  * your test or eval results

Pick one decision: **Go** (criteria met, review passed, nothing blocking), **No-Go** (a blocking item remains), or **Conditional Go** (shipping with named conditions to resolve later). Back it with at least two sentences that cite specific evidence, not "everything looks fine." The samples include a `docs/go-no-go-checklist.md` template you fill in; for your own project, the written decision is the gate, not a heavy compliance form.

### 1.12. Sample Project A: Field Report Triage (Greenfield)

__Note

This is a sample, not an assignment. You are not required to use it. Build it only if you don’t have a better idea of your own.

__Note

Starter files are in `files/sample-greenfield/`: the report data, an answer key, the `lookup_owning_team` tool, a runnable driver, and tests, with the agent left for you to build. Your instructor releases the worked solution at the end of the capstone.

#### 1.12.1. Scenario

At **Meridian Logistics** , the field operations team gets a steady stream of free-text reports from drivers and depot technicians: equipment faults, safety issues, supply shortages, delays. A person reads each report, decides how urgent it is, and routes it. The volume is high, and the routine cases swamp the urgent ones.

#### 1.12.2. What to Build

A single `LlmAgent` reads one report and returns a structured triage result. In ADK 2.x one agent does the whole job:

  * It has the function tool `lookup_owning_team(category)`, which it calls to route the report to the team that owns it.

  * It sets a Pydantic `output_schema` like `TriageResult { report_id, category, severity, location, owning_team, summary, recommended_action }`, with `@field_validator` methods constraining `category` and `severity` to a fixed set.

The tool runs during the agent’s reasoning; the schema is enforced on its final answer. The driver runs the agent over each report and collects the results.

#### 1.12.3. Escalation Option

When the single agent works on one report, scale to a batch: fan out across many reports at once, then route the high-severity ones to a deeper extraction step. Multi-step fan-out and conditional routing like that are where an ADK `Workflow` graph fits (see the _Workflow graph_ row in the Phase 2 escalation table for the specific constructs). Add this only if your plan calls for it.

#### 1.12.4. Data and Evidence

Write or generate a dozen sample reports. Keep an answer key (the expected category and severity for each) in a **separate file** the agent never reads. Build an eval set from the answer key and show the agent’s `severity` ordering is correct.

### 1.13. Sample Project B: Pricing Quote Wrapper (Brownfield)

__Note

This is a sample, not an assignment. You are not required to use it. Build it only if you don’t have a better idea of your own.

__Note

Starter files are in `files/sample-brownfield/`: the black-box `pricing_engine.py`, its contract, sample orders, a runnable driver, and tests, with the wrapper and agent left for you to build. Your instructor releases the worked solution at the end of the capstone.

#### 1.13.1. Scenario

At **Meridian Logistics** , the sales desk quotes freight with an aging in-house pricing engine. It exposes one function, `quote(order) → dict`, and returns raw quotes in a fixed shape. The output has quirks: no tax, a currency that’s sometimes missing, a unit price on only some lanes, and a null price for an unrecognized SKU. You can’t change it. A rep cleans up each quote by hand before sending it to a customer.

#### 1.13.2. The Black Box

The pricing engine is the black box. You wrap it, you don’t touch it.

  * Route every call through one function-tool wrapper around `quote()`

  * You may mock it for tests; the sample freezes the engine’s delivered output as a baseline and asserts every quote still matches it, so editing the engine breaks the test

  * Never change its logic or its output

#### 1.13.3. What to Build

A single `LlmAgent` turns a raw quote into a customer-ready one. In ADK 2.x one agent both calls the tool and emits the schema:

  * It has the function-tool wrapper over `quote()`. It calls the wrapper with the order_id and reads the raw quote from the tool result.

  * It sets a Pydantic `output_schema` `CustomerQuote { quote_id, sku, quantity, subtotal, currency, tax, total, anomalies, explanation }` and maps the raw quote’s fields onto it. A `@model_validator` computes `tax` and `total` and fills `anomalies` (missing currency, no price for the lane), so the money math is right no matter what the model returned.

Every change happens after the agent receives the raw quote. The transformation is yours; the quote is inherited.

#### 1.13.4. The Boundary and the Regression Check

  * Write the one-page contract describing `quote()` and its output, ending with _What This Agent Does Not Touch_.

__Note

If you are using Sample B, the starter files include a completed contract at `contracts/pricing-engine-contract.md`. Review it. It fulfills this requirement. For your own project, write a new contract for your black-box system.

  * Record `quote()’s raw output for your sample orders before you integrate, then assert it’s identical after. Your wrapper reads; it never writes back.

### 1.14. Stretch Challenges

Reach for these only after you meet every success criterion.

  * **Add a guardrail.** Use a `before_model_callback` or a plugin to block prompt injection or redact secrets in your agent’s input.

  * **Persist across runs.** Add a memory service so the agent recalls context from earlier sessions.

  * **Deploy it.** Serve your agent with `adk api_server` and deploy it with `adk deploy agent_engine`, then trace one run with OpenTelemetry to Cloud Trace.

  * **Split a specialist out.** If your agent has a clearly separable role, expose it over A2A (Agent-to-Agent) with `to_a2a` and call it with a `RemoteA2aAgent`. Install the A2A extra first with `uv add "google-adk[a2a]"`; the imports fail on the base install. A2A is experimental, so treat this as advanced.

### 1.15. Appendix: ADK Quick Reference

Construct | Use it for  
---|---  
`LlmAgent` (`Agent`) | The core agent: name, model, instruction, tools, `output_schema`, `output_key`  
Pydantic `output_schema` | Constraining the agent to a typed, validated result; in ADK 2.x it runs alongside `tools` on the same agent  
Function tool | A typed Python function the agent can call; return a `{status, …​}` dict  
`McpToolset` | Connecting an external MCP (Model Context Protocol) server (use `StdioConnectionParams` for a local stdio server)  
Session state (`temp:` / `user:` / `app:`) | Remembering within a run, per user, or per app  
Memory service + `load_memory` | Remembering across runs  
`Workflow` graph (`START`/`edges`, `FunctionNode`, `JoinNode`, `@node`) | Deterministic multi-step orchestration: fixed sequences, routing, and joins  
`SequentialAgent` / `ParallelAgent` / `LoopAgent` | Legacy templated workflows, superseded by the `Workflow` graph in ADK 2.0  
`sub_agents` / `AgentTool` | Multi-agent teams: LLM-driven transfer, or an agent called as a tool  
Callbacks / `BasePlugin` | Guardrails and cross-cutting logic at agent, model, or tool boundaries  
`pytest` on tools and schemas | Deterministic, key-free unit tests: call tool functions directly and exercise the Pydantic validators  
`InMemoryRunner` | Integration-style runs against the live model, in pytest or a driver script  
`adk web` / `adk eval` | The Dev UI, and running evaluation sets  
  
  * Each lab and project is its own `uv` project: `uv sync` to set up, `uv run` to execute.

  * The model comes from the `ADK_MODEL` environment variable; Gemini Flash is a good default.

  * Get a Gemini API key from Google AI Studio: <https://aistudio.google.com>

  * ADK documentation: <https://adk.dev>

### 1.16. What You’re Proving

The capstone demonstrates a single capability: you can take an ambiguous, real-world task and deliver a working agentic system in Google ADK, end to end. Pick a problem that matters, own the design, and be ready to defend your trade-offs in the showcase.
